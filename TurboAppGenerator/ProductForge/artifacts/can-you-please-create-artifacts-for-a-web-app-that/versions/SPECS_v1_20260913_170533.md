## 1. Project Structure

Single self-contained, client-only static artifact. No build step, no package manager required to *run* the app. A Node.js script exists only as dev-time tooling to generate the bundled mock dataset — it is not shipped or executed by the app at runtime.

```
oem-dealer-platform/
├── index.html                     # Single entry point; tab shell (Grid / Analytics / Chat) + Viewing-As selector
├── README.md                      # How to run (open index.html or serve statically), how to regenerate mock data
│
├── css/
│   └── styles.css                 # Small set of custom rules Tailwind utility classes can't express
│                                   # (e.g., custom scrollbar for grid, chat bubble tails). No Tailwind build — Tailwind loaded via CDN in index.html.
│
├── js/
│   ├── config.js                  # App-wide constants (page size, max records, data file path, schemaVersion). See Section 3.
│   ├── main.js                    # Bootstraps app: loads data, initializes dataStore, wires ui.* modules, sets default viewingAs
│   ├── dataStore.js               # In-memory store: raw entities, integrity checks, indexes, getScopedRecords()
│   ├── services.js                # services.* contract layer (getVehicles, getDealers, getAnalyticsSummary, etc.) — spec'd in Part 2
│   ├── chatbotEngine.js           # Rule-based intent matcher + resolvers; consumes services.* only — spec'd in Part 2
│   │
│   ├── ui/
│   │   ├── viewingAs.js           # Renders + manages the global "Viewing As" role/dealer selector control
│   │   ├── grid.js                # Renders data grid tab: table, sort/filter controls, pagination controls
│   │   ├── charts.js              # Renders analytics tab: Chart.js chart instances bound to services.getAnalyticsSummary()
│   │   └── chat.js                # Renders chat tab: message list, input box, calls chatbotEngine.handleMessage()
│   │
│   └── utils/
│       ├── validators.js          # viewingAs validation, record validation helpers (fail-closed checks)
│       └── format.js              # Currency/date/number formatting helpers used across grid/charts/chat
│
├── data/
│   └── mockData.json              # Bundled static dataset: schemaVersion + oem + dealers[] + vehicles[]. Loaded once via fetch() at startup.
│
├── scripts/
│   └── generate-mock-data.js      # Node.js (dev-only, NOT shipped/served). Regenerates data/mockData.json with referential integrity.
│                                   # Run manually: `node scripts/generate-mock-data.js`. Requires Node 18+.
│
└── tests/
    └── smoke-checklist.md         # Manual smoke-test checklist (Section 15, Part 4)
```

**Rules governing this structure:**
- No `node_modules/`, no `package.json` is required to **run** the app — `index.html` opened directly (or served statically) must work standalone, loading Tailwind and Chart.js from CDN and `mockData.json` via a relative `fetch()`.
- `scripts/generate-mock-data.js` is the only file in the repo requiring Node.js, and only for regenerating `data/mockData.json`. It must never be referenced by `index.html` or any browser-loaded script.
- Script load order in `index.html` is fixed and must be: `config.js` → `dataStore.js` → `services.js` → `chatbotEngine.js` → `utils/*.js` → `ui/*.js` → `main.js` (all as plain `<script>` tags, no ES module bundler required; `defer` attribute on all).
- **[DECISION NEEDED]** Whether to convert `js/*.js` files to native ES modules (`<script type="module">`) instead of global namespace objects (`dataStore`, `services`, `ui`, `chatbotEngine` as `window`-level objects). This spec assumes **global namespace objects**, matching TRD Section 3's `dataStore.* / services.* / ui.*` naming — not ES modules — to avoid CORS-on-`file://` issues when a user opens `index.html` directly without a server.

| Auth | None | — | Per guardrails and TRD Section 2 |

### Why these exact pins?
- Chart.js is pinned to an exact version (`4.4.4`) because chart config APIs can change between minor versions and this app hard-codes chart config objects against that API surface — an unpinned CDN URL risks silent breakage on a future Chart.js release.
- Tailwind is **not** pinned because the Play CDN product does not support version-locked utility generation the way a build-time Tailwind install would; this is an accepted prototype-only trade-off (see Section 14, Part 4, for the production remediation: install Tailwind via npm + PostCSS build when this app graduates past prototype).

## 3. Environment Configuration

**There are no runtime environment variables.** This is a static client-only application with no server process, no build step, and no `.env` file. `process.env` must never appear in any file under `js/`.

### 3.1 Application Configuration Constants (`js/config.js`)

All tunables are hard-coded JS constants (not env vars), loaded first in script order so every other module can reference `window.APP_CONFIG`.

```js
// js/config.js
window.APP_CONFIG = Object.freeze({
  SCHEMA_VERSION: "1.0.0",           // Must match data/mockData.json's top-level schemaVersion exactly
  DATA_FILE_PATH: "./data/mockData.json",

  // Pagination defaults (see Section 9, Part 3 — Grid Behavior Spec)
  DEFAULT_PAGE_SIZE: 50,
  MAX_PAGE_SIZE: 200,

  // Dataset size guardrails (see Section 4.5) — used by integrity checks to warn, not to hard-fail
  EXPECTED_MIN_VEHICLES: 2000,
  EXPECTED_MAX_VEHICLES: 3000,
  EXPECTED_MIN_DEALERS: 8,
  EXPECTED_MAX_DEALERS: 10,

  // Chatbot (see Section 7, Part 2)
  CHAT_MAX_HISTORY_MESSAGES: 50,     // In-memory chat transcript cap per session; oldest messages dropped beyond this

  // Viewing-As mock roles (see Section 6, Part 2)
  VALID_ROLES: ["OEM_ADMIN", "OEM_ANALYST", "DEALER_PRINCIPAL", "DEALER_STAFF"],
});
```

### 3.2 Mock Data Generation Script Parameters (dev-only, Node.js CLI — not app env vars)

`scripts/generate-mock-data.js` accepts optional CLI flags (with defaults) — these are **not** consumed by the browser app and must not be read via `process.env` anywhere in `js/`:

| Flag | Default | Description |
|---|---|---|
| `--dealerCount` | `9` | Number of dealers to generate (must fall within 8–10 per Section 4.5) |
| `--vehicleCount` | `2500` | Total vehicles to generate across all dealers (must fall within 2000–3000) |
| `--seed` | `42` | Deterministic RNG seed — reruns with the same seed must produce identical output, so chatbot test fixtures (Part 2/4) don't drift between regenerations |
| `--outFile` | `./data/mockData.json` | Output path |

**Rule:** Running the script with the same `--seed` value must be idempotent (byte-identical output) to keep any hard-coded chatbot QA fixtures valid across regenerations.

### 3.3 What is explicitly NOT configured

- No API base URL (no API exists).
- No database connection string (no database exists).
- No auth client ID/secret (no auth exists).
- No feature flags service (not requested; if needed later, a plain constant in `config.js` is the pre-approved mechanism, not a remote flag service).

## 4. Data Models & Schema

### 4.0 No SQL Database — Rationale and Equivalent Contract

Per TRD Section 3, this build has **no database** (SQLite is the pre-approved next step only if server-side persistence becomes an explicit requirement — it is not in this build). There is therefore **no SQL DDL**. The equivalent "schema" is:

1. The **JSON Schema shape** of `data/mockData.json` (the on-disk/on-CDN data contract), and
2. The **TypeScript-style type definitions** used by every JS module for the in-memory representation of that data (documentation-only types — this is plain JS at runtime, no TS compiler in the toolchain), and
3. The **in-memory index structures** `dataStore.js` must build at load time, which serve the role a database index would serve.

All three are specified below and are binding — an implementer must not deviate from these field names/types without updating this document.

### 4.1 Domain Decision (locked for this build)

Per TRD Section 2, the PRD's open domain question is resolved as **Vehicle Inventory**. All entities below are Vehicle-Inventory-specific, not generic "Record" entities as PRD Section 5 described illustratively.

### 4.2 Top-Level File Shape — `data/mockData.json`

```jsonc
{
  "schemaVersion": "1.0.0",          // Must equal APP_CONFIG.SCHEMA_VERSION; dataStore init fails closed if mismatched (see 4.6)
  "generatedAt": "2025-01-15T00:00:00.000Z",  // ISO-8601, set by generate-mock-data.js at generation time
  "generatorSeed": 42,               // Echoes the --seed used, for traceability/debugging only

  "oem": { /* OEM object, exactly one — see 4.3.1 */ },
  "dealers": [ /* Dealer[], 8–10 entries — see 4.3.2 */ ],
  "vehicles": [ /* Vehicle[], 2000–3000 entries — see 4.3.3 */ ]
}
```

### 4.3 Entity Definitions (TypeScript-style, documentation only)

#### 4.3.1 OEM

```typescript
interface OEM {
  oemId: string;         // Format: "OEM-001" — exactly one OEM instance exists in this build
  name: string;          // e.g., "Northwind Motors" (fictional; generated by script)
  regions: string[];     // List of region codes this OEM operates in, e.g. ["NA-WEST", "NA-EAST", "NA-CENTRAL"]
}
```

- Exactly **one** OEM object exists per dataset (not an array at the top level — single-tenant-root assumption for this prototype, consistent with PRD's OEM-as-tenant-root model).

#### 4.3.2 Dealer

```typescript
interface Dealer {
  dealerId: string;      // Format: "DLR-001".."DLR-010", stable, generated by script — never generated at runtime
  oemId: string;         // FK -> OEM.oemId; must equal the single OEM's oemId (validated at load, see 4.6)
  name: string;          // e.g., "Riverside Auto Group"
  region: string;        // Must be one of OEM.regions (validated at load, see 4.6)
  city: string;
  state: string;         // 2-letter US state code (illustrative; not geographically load-bearing)
}
```

- Count constraint: **8–10 Dealer objects** (Section 4.5).
- `dealerId` values must be sequential and zero-padded to 3 digits: `DLR-001`, `DLR-002`, ... `DLR-010`.

#### 4.3.3 Vehicle

```typescript
type VehicleStatus = "in-stock" | "sold" | "in-transit" | "reserved";

interface Vehicle {
  vehicleId: string;       // Format: "VEH-00001".."VEH-99999", zero-padded to 5 digits, sequential, generated by script
  vin: string;             // 17-char synthetic VIN (generated, not a real-world-valid checksum — illustrative only)
  oemId: string;            // FK -> OEM.oemId (denormalized; must match the single OEM)

  dealerId: string;         // FK -> Dealer.dealerId — the sole tenant-isolation boundary for this record
  dealerName: string;       // DENORMALIZED from Dealer.name at generation time. See 4.4 refresh rule.
  region: string;           // DENORMALIZED from Dealer.region at generation time. See 4.4 refresh rule.

  make: string;             // e.g., "Northwind" (fictional make; illustrative)
  model: string;
  year: number;              // 4-digit year, integer
  trim: string;

  status: VehicleStatus;
  price: number;             // USD, 2 decimal places, > 0
  cost: number;               // USD, 2 decimal places, > 0, <= price (validated at load, see 4.6)

  dateReceived: string;      // ISO-8601 date (YYYY-MM-DD), <= dateSold if present, <= generatedAt
  dateSold: string | null;   // ISO-8601 date or null; null unless status === "sold"

  // daysInInventory is explicitly NOT part of the JSON file — see 4.3.4 (computed field)
}
```

- Count constraint: **2000–3000 Vehicle objects** (Section 4.5), distributed across the 8–10 dealers (need not be perfectly even; script may vary counts per dealer, but every dealer must have at least 1 vehicle so no dealer view is ever structurally empty).
- `vehicleId` values must be globally sequential and zero-padded to 5 digits: `VEH-00001` ... `VEH-99999`. Never re-generated or re-assigned at runtime.
- **Business rule (from TRD Section 7, referenced here for schema completeness):** if `status === "sold"`, `dateSold` **must** be non-null and `>= dateReceived`; if `status !== "sold"`, `dateSold` **must** be `null`. This is validated at load per Section 4.6.

#### 4.3.4 Computed / Derived Fields (never stored in JSON)

```typescript
interface VehicleWithComputed extends Vehicle {
  daysInInventory: number;   // Computed once at dataStore load time, NOT recomputed reactively, NOT persisted back to JSON
}
```

**Computation rule (locked):**
```
referenceDate = (vehicle.status === "sold") ? vehicle.dateSold : dataStore.loadTimestamp
daysInInventory = floor( (referenceDate - vehicle.dateReceived) in days )
```
- `dataStore.loadTimestamp` is captured **once**, at app initialization (`Date.now()` at the moment `dataStore.init()` runs), and reused for every in-stock/reserved/in-transit vehicle's `daysInInventory` calculation for the entire session. It does **not** update live as wall-clock time passes during a long-lived session — this is an explicit, documented simplification for the prototype (a page refresh reloads data and recalculates against a fresh `loadTimestamp`).
- `daysInInventory` is computed exactly once, immediately after load+integrity-check, and attached to each in-memory `Vehicle` object as a plain property. It is derived data living only in `dataStore`'s in-memory array — it must never be written back into `data/mockData.json`.

### 4.4 Denormalization & Refresh Rule

`Vehicle.dealerName` and `Vehicle.region` are **intentionally denormalized** copies of `Dealer.name` and `Dealer.region`, written **once by `generate-mock-data.js`** at generation time.

**Refresh rule (locked, per Database Engineer input):**
- These fields are **never re-derived at runtime** by the browser app.
- If a future change to a `Dealer`'s `name` or `region` is needed, it must be made by re-running `generate-mock-data.js` (which regenerates both the `Dealer` record and every dependent `Vehicle.dealerName`/`Vehicle.region` in the same pass), not by hand-editing `mockData.json` or patching values in the browser.
- `dataStore`'s integrity check (4.6) must verify these denormalized fields are still consistent with the referenced `Dealer` at load time and treat a mismatch as a data integrity failure (exclude + `console.error`), since a mismatch means the JSON file was hand-edited inconsistently.

### 4.5 Cardinality / Sizing Constraints (locked)

| Entity | Count | Enforced by |
|---|---|---|
| OEM | exactly 1 | Generation script; `dataStore.init()` warns via `console.warn` if `!= 1` but does not hard-fail (defensive only) |
| Dealer | 8–10 | Generation script hard-enforces via CLI validation; `dataStore.init()` logs `console.warn` (not a hard fail) if outside range, since a slightly-off count doesn't break functionality |
| Vehicle | 2000–3000 | Generation script hard-enforces via CLI validation; `dataStore.init()` logs `console.warn` if outside range |

These are **soft** checks at app-load time (warn, don't block) and **hard** checks at generation time (script refuses to write a file outside range) — the distinction matters because the app must still run against a hand-tweaked or older dataset file during development even if counts drift slightly.

### 4.6 Referential Integrity Validation (executed by `dataStore.init()`, at load time — every session)

This is the closest thing this prototype has to a foreign-key constraint, and it must run in code, every time, not be assumed from clean data:

```
On dataStore.init(rawData):
  1. Validate rawData.schemaVersion === APP_CONFIG.SCHEMA_VERSION
     -> if mismatch: console.error, ABORT init (fail closed — do not attempt to load an incompatible shape)

  2. Validate exactly one OEM object exists at rawData.oem
     -> if missing/malformed: console.error, ABORT init

  3. For each Dealer in rawData.dealers:
     a. dealer.oemId must equal rawData.oem.oemId
        -> if mismatch: EXCLUDE this dealer, console.error(dealerId, reason)
     b. dealer.region must be included in rawData.oem.regions
        -> if mismatch: EXCLUDE this dealer, console.error(dealerId, reason)
     c. dealer.dealerId must be unique across all dealers
        -> if duplicate: EXCLUDE the later duplicate, console.error

  4. For each Vehicle in rawData.vehicles:
     a. vehicle.dealerId must resolve to a Dealer that survived step 3
        -> if not found: EXCLUDE this vehicle, console.error(vehicleId, reason)
     b. vehicle.dealerName must exactly equal the resolved Dealer.name
        -> if mismatch: EXCLUDE this vehicle, console.error(vehicleId, reason: "denormalization drift")
     c. vehicle.region must exactly equal the resolved Dealer.region
        -> if mismatch: EXCLUDE this vehicle, console.error(vehicleId, reason: "denormalization drift")
     d. vehicle.oemId must equal rawData.oem.oemId
        -> if mismatch: EXCLUDE, console.error
     e. vehicle.vehicleId must be unique across all vehicles
        -> if duplicate: EXCLUDE the later duplicate, console.error
     f. Business rule check (Section 4.3.3): status/dateSold consistency
        -> if violated: EXCLUDE this vehicle, console.error(vehicleId, reason: "status/dateSold inconsistency")
     g. cost <= price
        -> if violated: EXCLUDE this vehicle, console.error(vehicleId, reason: "cost exceeds price")

  5. Log a single summary line at the end:
     console.warn(`dataStore.init: loaded ${keptDealers}/${totalDealers} dealers, ${keptVehicles}/${totalVehicles} vehicles. ${excludedCount} records excluded — see errors above.`)

  6. Compute daysInInventory for every surviving vehicle (Section 4.3.4), attach in place.

  7. Build indexes (Section 4.7).

  8. Mark dataStore.isReady = true. Any service call made before this must fail closed (see Part 2, Section 5).
```

**Excluded records are dropped from the in-memory store entirely for the session** — they never appear in Grid, Charts, or Chatbot results. This is intentional: a corrupted record scoped incorrectly is worse than a missing record.

### 4.7 In-Memory Indexes (built once, at end of `dataStore.init()`)

These are the prototype's equivalent of database indexes — required, not optional, because `services.*` (Part 2) must not do O(n) scans of the full vehicle array on every call once the store is loaded:

```typescript
// Internal to dataStore.js — not part of the public dataStore.* contract (that's Part 2)
interface DataStoreIndexes {
  dealersById: Map<string, Dealer>;                 // dealerId -> Dealer
  vehiclesByDealerId: Map<string, VehicleWithComputed[]>;  // dealerId -> Vehicle[]
  vehicleById: Map<string, VehicleWithComputed>;    // vehicleId -> Vehicle
  allVehicles: VehicleWithComputed[];               // flat array, post-integrity-check, post-computed-fields
  allDealers: Dealer[];                             // flat array, post-integrity-check
  oem: OEM;
  loadTimestamp: number;                            // epoch ms, captured once (Section 4.3.4)
}
```

- `vehiclesByDealerId` must be built such that every surviving `Dealer.dealerId` has an entry (even if empty array) — downstream code (grid empty-state, Section 9/Part 3) must be able to rely on `Map.get(dealerId)` never returning `undefined` for a valid dealer, only an empty array at worst.

### 4.8 Entity Relationship Diagram (conceptual, ASCII)

```
┌──────────────┐        1        ┌──────────────┐        1        ┌──────────────┐
│     OEM      │ ───────────────▶│    Dealer    │◀─────────────── │   Vehicle    │
│  (exactly 1) │      owns        │  (8–10)      │      *          │ (2000–3000)  │
└──────────────┘                 └──────────────┘                 └──────────────┘
     oemId  ◀────────────────────────  oemId (FK)                     dealerId (FK)
                                        region ⊂ OEM.regions           dealerName (denorm, write-once)
                                                                       region (denorm, write-once)
                                                                       oemId (FK, denorm)
```

- OEM → Dealer: one-to-many, enforced at load (4.6.3a).
- Dealer → Vehicle: one-to-many, enforced at load (4.6.4a); **this is the primary tenant-isolation boundary** used by the Viewing-As mock scoping model (full spec in Part 2, Section 6).
- No many-to-many relationships exist in this data model.
- No Vehicle-to-Vehicle relationships exist (e.g., no trade-in linkage) — out of scope per PRD's domain-agnostic-then-resolved-to-inventory decision; not requested anywhere upstream.

## 5. Service Contract Design — Complete API Specifications

There is no HTTP transport in this build (per TRD §2/§3). The `dataStore.*` and `services.*` module boundary **is** the API surface and is specified below with the same rigor as an HTTP contract: every function has a signature, a request/response schema, logical status codes, error conditions, and business rules. An AI coding agent must implement exactly this contract — no additional endpoints, no additional parameters, no silent behavior changes.

---

### 5.1 API Design Principles (apply to every endpoint below)

**Call convention:** All `services.*` functions are **async** (return `Promise`) for interface stability, even though execution is synchronous against in-memory data — this keeps calling code (UI layer) agnostic if a real backend is substituted later. All `dataStore.*` functions are **synchronous** (internal layer only; never called directly by `ui.*`).

**Response envelope (all `services.*` functions that return collections):**
```ts
interface ServiceResult<T> {
  data: T;
  meta: Record<string, any>; // shape defined per-endpoint below
}
```

**Logical status codes** (no HTTP transport exists; these are the equivalent semantic outcomes every endpoint must map to):

| Logical Code | Meaning | Return Behavior |
|---|---|---|
| `OK` | Success, ≥1 result | `{ data: [...], meta: {...} }` |
| `OK_EMPTY` | Success, valid query, 0 matching results (legitimate) | `{ data: [], meta: {...totalCount:0} }` — **no console log** |
| `FAIL_CLOSED_EMPTY` | `viewingAs` failed validation | `{ data: [], meta: {...scopeWarning:true} }` + `console.error(...)` |
| `BAD_REQUEST` | Malformed/missing param, wrong type, unknown filter/sort field | `throw new ServiceError(code, message, details)` |
| `FATAL` | `dataStore` not initialized, or dataset failed to load | `throw new ServiceError(code, message)` — caller must render app-level error state |

**Error type (shared across all endpoints):**
```ts
class ServiceError extends Error {
  code: string;              // e.g. "INVALID_PARAM_TYPE", "DATASTORE_NOT_INITIALIZED"
  details?: Record<string, any>;
  constructor(code: string, message: string, details?: Record<string, any>);
}
```

**Hard rule (per Backend API Engineer directive):** Exceptions are thrown **only** for programmer/integration errors (bad param types, missing required params, unknown enum values, calling before `dataStore.init()` resolves). A legitimate empty result (`OK_EMPTY`) and an invalid-scope result (`FAIL_CLOSED_EMPTY`) are **never** thrown — always returned as normal `ServiceResult` objects. `undefined`/`null` is never returned in place of `data`; `data` is always `[]`, `{}`, or a concrete typed object.

**Shared type (referenced throughout; full entity schemas in Section 4):**
```ts
type Role = "OEM_ADMIN" | "OEM_ANALYST" | "DEALER_PRINCIPAL" | "DEALER_STAFF";

interface ViewingAs {
  role: Role;
  dealerId: string | null;
  // null is VALID only for role = OEM_ADMIN | OEM_ANALYST
  // non-null is REQUIRED for role = DEALER_PRINCIPAL | DEALER_STAFF
}
```

**Single Source of Truth Rule (mandatory, per Full Stack Developer directive):** Every `services.*` endpoint below that returns vehicle-derived data (grid, analytics, chatbot) MUST obtain its working record set by calling `dataStore.getScopedRecords(viewingAs)` (5.2.2) — directly or transitively — and MUST NOT read `dataStore`'s raw internal arrays through any other path. Grid, Chart, and Chatbot are guaranteed to agree because they share this one function.

### 5.2 `dataStore.*` — Internal Data Layer API

#### 5.2.1 `dataStore.init()`

**Method:** CALL (async) — must be invoked exactly once at app bootstrap, before any other `dataStore.*` or `services.*` call.

**Request Schema:** none (no params)

**Preconditions:** none — this is the bootstrap call.

**Success Response (`OK`):**
```ts
{
  initialized: true,
  recordCounts: { vehicles: number, dealers: number },
  integrityIssues: IntegrityIssue[]   // may be empty array; see 5.2.5
}
```

**Fatal Error Responses (`FATAL`):**

| Code | Trigger |
|---|---|
| `DATASET_LOAD_FAILURE` | Bundled JSON file(s) fail to fetch or fail to `JSON.parse` |
| `INTEGRITY_CHECK_FAILURE` | 100% of vehicle records fail referential integrity (zero valid records remain after check — catastrophic, not partial) |

**Business Rules:**
- On success, populates internal state: `_state.vehicles`, `_state.dealers`, `_state.oem`, `_state.initialized = true`, `_state.integrityReport`.
- Runs the referential integrity pass defined in 5.2.5 as part of init — **partial** integrity failures (some invalid records) do NOT throw; invalid records are excluded from `_state.vehicles` and logged via `console.error`, and `init()` still resolves with `OK`.
- Any `dataStore.*` or `services.*` function called before `init()` resolves, or after a `FATAL` rejection, must throw `ServiceError("DATASTORE_NOT_INITIALIZED", ...)`.
- Caller (UI bootstrap) is responsible for rendering a full-app error state on `FATAL` — no partial UI, no fallback dataset.

#### 5.2.2 `dataStore.getScopedRecords(viewingAs)`

**Method:** CALL (sync, pure — no I/O, no mutation)

**Request Schema:**
```ts
function getScopedRecords(viewingAs: ViewingAs): Vehicle[]
```

**Preconditions:** `dataStore.init()` has resolved.

**Success Response (`OK` / `OK_EMPTY`):** `Vehicle[]` — filtered per rules below. Never `null`/`undefined`; an empty array is a valid result.

**Fail-Closed Response (`FAIL_CLOSED_EMPTY`):** `[]` (empty array) + `console.error("[dataStore.getScopedRecords] invalid viewingAs", viewingAs)`

**Business Rules (filtering logic, evaluated in order):**
1. `viewingAs.role` not in the `Role` enum → **fail closed**.
2. `role ∈ {OEM_ADMIN, OEM_ANALYST}` and `dealerId === null` → return **all** vehicles (full OEM-wide scope).
3. `role ∈ {OEM_ADMIN, OEM_ANALYST}` and `dealerId` is a non-null value that resolves to a known dealer → return vehicles filtered to that single `dealerId` (supports OEM users drilling into one dealer's view). **[ASSUMPTION]** — TRD/PRD do not explicitly describe this drill-down mode; included because the Viewing-As selector (Section 8, Part 3) must let an OEM user simulate "viewing as a specific dealer," and this is the only mechanism available without inventing a second parameter. Flagged for confirmation.
4. `role ∈ {DEALER_PRINCIPAL, DEALER_STAFF}` and `dealerId` is null → **fail closed** (these roles must always carry a concrete dealer).
5. `role ∈ {DEALER_PRINCIPAL, DEALER_STAFF}` and `dealerId` does not resolve to a known dealer → **fail closed**.
6. `role ∈ {DEALER_PRINCIPAL, DEALER_STAFF}` and `dealerId` resolves to a known dealer → return vehicles filtered to that `dealerId` only.
7. Any other combination not covered above → **fail closed** (default-deny).

#### 5.3.1 `services.getVehicles(viewingAs, options)`

**Method:** CALL (async)

**Request Schema:**
```ts
interface GetVehiclesOptions {
  filters?: {
    status?: "in-stock" | "sold" | "in-transit" | "reserved";
    dealerId?: string;          // intersected with scope, never a bypass — see Business Rules
    make?: string;
    model?: string;
    year?: number;
    region?: string;
    dateReceivedFrom?: string;  // ISO date
    dateReceivedTo?: string;    // ISO date
    dateSoldFrom?: string;      // ISO date
    dateSoldTo?: string;        // ISO date
  };
  sort?: {
    field: "vehicleId" | "make" | "model" | "year" | "price" | "dateReceived" | "dateSold" | "daysInInventory" | "status";
    direction: "asc" | "desc";
  };
  pagination?: {
    page?: number;      // default 1
    pageSize?: number;  // default 50, max 200
  };
}

function getVehicles(viewingAs: ViewingAs, options?: GetVehiclesOptions): Promise<ServiceResult<Vehicle[]>>
```

**Preconditions:** `dataStore.init()` resolved.

**Success Response (`OK`):**
```ts
{
  data: Vehicle[],
  meta: {
    totalCount: number,     // count after filters, before pagination
    page: number,
    pageSize: number,
    totalPages: number,
    scopeWarning: false
  }
}
```

**Empty Response (`OK_EMPTY`)** — valid query, zero matches (including requesting a `page` beyond `totalPages`):
```ts
{ data: [], meta: { totalCount: 0, page: <requested>, pageSize: <resolved>, totalPages: 0, scopeWarning: false } }
```

**Fail-Closed Response (`FAIL_CLOSED_EMPTY`):**
```ts
{ data: [], meta: { totalCount: 0, page: 1, pageSize: <resolved default>, totalPages: 0, scopeWarning: true } }
```
+ `console.error` logged by the underlying `dataStore.getScopedRecords` call.

**Error Responses (`BAD_REQUEST`, thrown):**

| Code | Trigger |
|---|---|
| `INVALID_FILTER_FIELD` | `filters` contains a key not in the whitelist above |
| `INVALID_SORT_FIELD` | `sort.field` not in the allowed enum |
| `INVALID_PARAM_TYPE` | `pagination.page`/`pageSize` not a positive integer, `year` not a number, date filters not valid ISO date strings |

**Business Rules:**
- Working set = `dataStore.getScopedRecords(viewingAs)` — filters/sort/pagination are applied **after** scoping, never before.
- `filters.dealerId`, if provided, is **intersected** with the caller's scope — it can only narrow an OEM-wide scope down to a specific dealer; it can never widen a dealer-scoped session to another dealer's data. If `filters.dealerId` conflicts with an already-dealer-scoped `viewingAs` (i.e., requests a different dealer than the one the session is scoped to), the result is `OK_EMPTY` (not an error, not a leak).
- `pageSize` default = **50**; max = **200**. Requests above 200 are clamped to 200, not rejected.
- Default `sort` if omitted: `{ field: "vehicleId", direction: "asc" }`. **[ASSUMPTION]** — no default sort order is specified upstream; `vehicleId` ascending chosen as the most deterministic, domain-neutral default.
- `daysInInventory` is a derived field (computed at `dataStore.init()` load time per Section 4 data model) and is filterable/sortable like any other field, but is never present in the source JSON.

### 5.8 Cross-Cutting Business Rules Summary

1. **Single scoping function:** All vehicle-derived data (grid, all three analytics endpoints, chatbot) must resolve through `dataStore.getScopedRecords(viewingAs)` — no endpoint filters the raw dataset independently.
2. **Fail-closed, not fail-open:** Any invalid `viewingAs` anywhere in the system returns an empty result + `console.error` — it never falls back to unscoped/"all data" access.
3. **Empty ≠ Error:** A valid query returning zero rows (`OK_EMPTY`) is never thrown as an exception and never logged as an error — only `FAIL_CLOSED_EMPTY` (invalid scope) and `BAD_REQUEST`/`FATAL` (programmer/system errors) produce console output.
4. **Pagination is always present:** `services.getVehicles` always returns full pagination `meta` regardless of dataset size, even though the dataset (~2,000–3,000 records per Section 4) never requires server-side paging.
5. **`filters.dealerId` can only narrow, never widen** a session's existing scope.
6. **No write/update endpoints are defined in this document.** PRD §3 (Sam Ortiz persona) implies dealer-staff field-level edit capability; TRD's scope resolution (§2) and the three core surfaces named in TRD §4 (Grid / Analytics / Chat) do not commit to editable grid behavior. **[DECISION NEEDED]:** confirm whether in-memory (session-only, non-persistent) grid editing is in scope before implementation begins. Until confirmed, the grid is **read-only** and no `services.updateVehicle` (or equivalent) function exists.

## 6. Frontend Component Specifications

### 6.1 `ui.appShell` (Root Component)

**Purpose:** Bootstraps the app, owns the tab container, orchestrates initial data load, renders the persistent "Viewing As" selector and global error banner.

**Props:** none (top-level; instantiated once from `index.html` inline script on `DOMContentLoaded`).

**Internal State:**
```ts
{
  activeTab: 'grid' | 'analytics' | 'chat';   // default: 'grid'
  bootstrapStatus: 'loading' | 'ready' | 'error';
}
```

**Behavior:**
1. On load: render skeleton shell (tab bar + empty content area + `ui.viewingAsSelector` in header) immediately, `bootstrapStatus = 'loading'`.
2. Call `dataStore.init()` (synchronous per §5 call convention: `dataStore.*` is sync). Wrap in try/catch.
   - Success → `bootstrapStatus = 'ready'`, emit `app:dataLoaded`, mount `ui.dataGridView` into content area for `activeTab`.
   - Failure (thrown `ServiceError` with code `FATAL`) → `bootstrapStatus = 'error'`, emit `app:dataLoadFailed`, render `ui.errorBanner` full-screen, **do not mount any tab**.
3. Tab click → set `activeTab`, unmount current tab component, mount the selected one (`ui.dataGridView` / `ui.analyticsView` / `ui.chatView`). Mounting/unmounting is cheap re-render, not component destruction of the underlying data — each tab component re-reads current `viewingAs` from `ui.viewingAsSelector.getCurrentViewingAs()` on mount.
4. Only one tab is ever mounted/rendered in the DOM at a time (others are `display:none` is **not** used — full unmount/remount to avoid stale DOM referencing stale data after a `viewingAs` change while a tab was hidden).

**Events:**
- Emits: `app:dataLoaded`, `app:dataLoadFailed`
- Listens: none

**Internal State:**

## 7. Business Logic & Algorithms

### 7.1 Viewing-As Validation Rule (Fail-Closed Gate)

This is the **single point of enforcement** referenced by TRD §8 and mandated by the Full Stack Developer's "one function" constraint. Every `services.*` function that accepts `viewingAs` must call this validator **first**, before touching `dataStore`.

```ts
type ViewingAs = { role: 'OEM Admin' | 'OEM Analyst' | 'Dealer Principal' | 'Dealer Staff'; dealerId: string | null };

const VALID_ROLES = ['OEM Admin', 'OEM Analyst', 'Dealer Principal', 'Dealer Staff'];
const OEM_SCOPED_ROLES = ['OEM Admin', 'OEM Analyst'];
const DEALER_SCOPED_ROLES = ['Dealer Principal', 'Dealer Staff'];

function isValidViewingAs(viewingAs: ViewingAs): boolean {
  if (!viewingAs || !VALID_ROLES.includes(viewingAs.role)) return false;
  if (OEM_SCOPED_ROLES.includes(viewingAs.role)) {
    return viewingAs.dealerId === null;               // OEM roles must NOT carry a dealerId
  }
  if (DEALER_SCOPED_ROLES.includes(viewingAs.role)) {
    return typeof viewingAs.dealerId === 'string'
      && dataStore.dealerExists(viewingAs.dealerId);   // must resolve to a real, loaded dealer
  }
  return false;
}
```

- Failure → logical code `FAIL_CLOSED_EMPTY`: return the endpoint's empty-shape response with `meta.scopeWarning = true`, and `console.error('[SCOPE] Invalid viewingAs rejected:', viewingAs)`. **Never** fall back to unscoped/all-records behavior under any circumstance — this is a hard invariant, not a default.

### 7.2 The Single Scoping Function

Per Full Stack Developer's mandate — this is the **only** function permitted to filter records by tenant. Grid, Analytics, and Chat all resolve to calls that pass through this function; no component and no other `services.*` function may independently re-implement dealer/OEM filtering.

```ts
// dataStore.* (synchronous, internal layer)
function getScopedRecords(viewingAs: ViewingAs): Vehicle[] {
  if (!isValidViewingAs(viewingAs)) return [];   // fail closed; caller (services.*) handles logging/logical code

  if (OEM_SCOPED_ROLES.includes(viewingAs.role)) {
    return dataStore._allVehicles;   // OEM roles: full cross-dealer visibility (single OEM in this dataset — §Data Models)
  }
  // Dealer-scoped roles: exactly one dealer's records
  return dataStore._allVehicles.filter(v => v.dealerId === viewingAs.dealerId);
}
```

- `services.getVehicles`, `services.getAnalyticsSummary`, and `services.getChatbotResponse` **must** call `dataStore.getScopedRecords(viewingAs)` as their first data-access step and apply all further filtering/sorting/aggregation/intent-matching **only** on the returned array. No function may read `dataStore._allVehicles` directly except this one.
- OEM Admin vs. OEM Analyst currently resolve to identical row-level scope (both see all dealers) — the distinction between them is reserved for field-level edit permission only (§7.4), not row visibility. **[DECISION NEEDED]**: confirm with stakeholders whether OEM Analyst should ever be row-restricted (e.g., to an assigned region) — PRD's Priya persona says "across all dealers in her region," which implies a region-level scope narrower than full OEM visibility. This prototype implements OEM Analyst as full-visibility (same as OEM Admin) because no region-assignment data model exists (no `assignedRegion` field on User in the PRD's conceptual model) — **flagged, not silently resolved.**

### 7.3 Grid Filter Algorithm

Filters are combined with logical **AND**. Each filter is independently optional (`null`/`''` = not applied).

```ts
function applyFilters(records: Vehicle[], filters: GridFilters): Vehicle[] {
  return records.filter(v => {
    if (filters.status && v.status !== filters.status) return false;
    if (filters.dealerId && v.dealerId !== filters.dealerId) return false;
    if (filters.region && v.region !== filters.region) return false;
    if (filters.search) {
      const needle = filters.search.trim().toLowerCase();
      if (needle.length === 0) return true;
      const haystack = `${v.vin} ${v.make} ${v.model}`.toLowerCase();
      if (!haystack.includes(needle)) return false;
    }
    return true;
  });
}
```

- `search` matches substring across `vin`, `make`, `model` only (not `trim`, not `dealerName`) — fixed scope, not user-configurable.
- `dealerId` filter control is only rendered/accepted for OEM-scoped `viewingAs`; if a Dealer-scoped `viewingAs` somehow submits a `dealerId` filter value, `services.getVehicles` must ignore it silently (it's already implicitly scoped by §7.2) rather than treat it as `BAD_REQUEST` — this avoids punishing a harmless no-op.
- Unknown filter keys (not in `{status, dealerId, region, search}`) → `BAD_REQUEST` (programmer error, per §5).

Must be validated with stakeholders before production.]** PRD states Dealer Staff "edits only fields he's permitted to" without naming the fields, and describes OEM Analyst and Dealer Principal only in terms of monitoring/reviewing, not explicit editing rights. The following matrix is a reasonable, documented default — not a discovered requirement:

Failing either check → `BAD_REQUEST` with message `"Field not editable for current viewing scope."` — **not** `FAIL_CLOSED_EMPTY` (this is a permission rule violation on a specific write, not an invalid scope object).

### 7.5 Field Validation Rules (Edit Commit)

Applied in `services.updateVehicleField`, in order, first failure wins (returns `BAD_REQUEST` with the specific message):

| Field | Rule |
|---|---|
| `status` | Must be one of `['in-stock','sold','in-transit','reserved']`. Must satisfy the status transition state machine (§7.9). |
| `price` | Must be a finite number `> 0`. Max 2 decimal places (reject, don't silently round). |
| `cost` | Must be a finite number `> 0`. |
| `dateSold` | If `status === 'sold'`: required, must be a valid ISO date, must be `>= dateReceived` of that same record, must be `<=` the dataset's `datasetGeneratedAt` (§7.6 reference date — cannot record a sale "in the future" relative to the mock snapshot). If `status !== 'sold'`: must be `null` — setting a non-null `dateSold` while status is not `sold` is `BAD_REQUEST`. |

`daysInInventory` is never directly editable (attempting to edit it is `BAD_REQUEST` — "field is derived and read-only").

### 7.6 Derived Field & Aggregation Formulas

**Reference date:** the bundled dataset JSON carries a top-level `datasetGeneratedAt: string` (ISO date, set once by the generation script — per Database Engineer's note). This is the fixed "now" used for all age calculations, ensuring deterministic values regardless of when a user opens the app.

```ts
function computeDaysInInventory(vehicle: Vehicle, datasetGeneratedAt: string): number {
  const start = new Date(vehicle.dateReceived);
  const end = vehicle.status === 'sold' && vehicle.dateSold
    ? new Date(vehicle.dateSold)
    : new Date(datasetGeneratedAt);
  const msPerDay = 1000 * 60 * 60 * 24;
  return Math.max(0, Math.floor((end.getTime() - start.getTime()) / msPerDay));
}
```
- Computed once at `dataStore.init()` for every loaded record and cached on the in-memory object (per Database Engineer: "computed at load time, not stored" — i.e., not part of the bundled JSON, but is part of the runtime `dataStore._allVehicles` shape for the session).
- **Recomputation trigger:** if `status` or `dateSold` is edited via the grid (§7.4), `services.updateVehicleField` must recompute `daysInInventory` for that record immediately after a successful validation, using the same function and the same static `datasetGeneratedAt` (not the browser's real current date).

**Chart aggregation algorithms** (all operate on `dataStore.getScopedRecords(viewingAs)` output — never on raw `_allVehicles`):

```ts
// statusBreakdown: count of vehicles per status value
function statusBreakdown(records: Vehicle[]): { labels: string[], counts: number[] } {
  const order = ['in-stock', 'reserved', 'in-transit', 'sold'];
  const counts = order.map(s => records.filter(r => r.status === s).length);
  return { labels: order, counts };
}

// inventoryAgeByDealer: average daysInInventory per dealer, OEM-scoped roles only
function inventoryAgeByDealer(records: Vehicle[]): { labels: string[], averages: number[] } {
  const byDealer = groupBy(records, r => r.dealerName);
  const labels = Object.keys(byDealer).sort();
  const averages = labels.map(name => {
    const group = byDealer[name];
    return round2(group.reduce((sum, r) => sum + r.daysInInventory, 0) / group.length);
  });
  return { labels, averages };
}

// avgPriceByMakeModel: average price grouped by "Make Model", top 10 by count, rest bucketed as "Other"
function avgPriceByMakeModel(records: Vehicle[]): { labels: string[], averages: number[] } {
  const grouped = groupBy(records, r => `${r.make} ${r.model}`);
  const entries = Object.entries(grouped)
    .map(([key, group]) => ({ key, avg: round2(group.reduce((s, r) => s + r.price, 0) / group.length), count: group.length }))
    .sort((a, b) => b.count - a.count);
  const top10 = entries.slice(0, 10);
  return { labels: top10.map(e => e.key), averages: top10.map(e => e.avg) };
  // Records beyond top 10 groups are simply not charted — no "Other" bucket in v1, to avoid a misleading
  // average-of-averages. [DECISION NEEDED if stakeholders want an "Other" aggregate bar added later.]
}

// inventoryTrend: count of vehicles received per calendar month, last 6 months relative to datasetGeneratedAt
function inventoryTrend(records: Vehicle[], datasetGeneratedAt: string): { labels: string[], counts: number[] } {
  const months = lastNMonthLabels(datasetGeneratedAt, 6);  // e.g. ["2025-01", ..., "2025-06"]
  const counts = months.map(m => records.filter(r => r.dateReceived.startsWith(m)).length);
  return { labels: months, counts };
}
```

`round2(n) = Math.round(n * 100) / 100`. `groupBy` is a standard array-to-map-of-arrays helper — no external library.

### 7.7 Chatbot Intent Catalog & Resolution Algorithm

Per TRD §3/§10: rule-based, enumerated intents only — **no free-form NLP, no LLM call**. Intents are checked **in the fixed priority order below**; the first pattern match wins. All intents execute exclusively against `dataStore.getScopedRecords(viewingAs)`.

```ts
type Intent =
  | 'HELP'
  | 'TOTAL_COUNT'
  | 'COUNT_BY_STATUS'
  | 'AVG_DAYS_IN_INVENTORY'
  | 'AVG_PRICE'
  | 'DEALER_COMPARISON'      // OEM-scoped roles only
  | 'CROSS_TENANT_REQUEST'   // guardrail intent — see below
  | 'UNRECOGNIZED';

interface IntentRule {
  intent: Intent;
  patterns: RegExp[];   // case-insensitive; first matching pattern within the intent wins
}
```

| Priority | Intent | Example Trigger Patterns | Resolution Logic |
|---|---|---|---|
| 1 | `CROSS_TENANT_REQUEST` | `/\b(dealer|dealership)\s+([a-z0-9\- ]+)\b/i` combined with a dealer name/id token that does **not** match the current `viewingAs` scope, when `viewingAs.role` is Dealer-scoped | See guardrail logic below — always short-circuits before other intents are checked. |
| 2 | `HELP` | `/^help$/i`, `/what can you (do|answer)/i` | Return static list of supported example questions. |
| 3 | `TOTAL_COUNT` | `/how many vehicles?( are there)?$/i`, `/total (vehicle|inventory) count/i` | `records.length` |
| 4 | `COUNT_BY_STATUS` | `/how many (are |vehicles )?(in[- ]stock|sold|in[- ]transit|reserved)/i` | Extract status token from match, count `records.filter(r => r.status === matchedStatus)` |
| 5 | `AVG_DAYS_IN_INVENTORY` | `/average days in inventory/i`, `/how long .* in inventory/i` | `round2(mean(records.map(r => r.daysInInventory)))` |
| 6 | `AVG_PRICE` | `/average price/i` | `round2(mean(records.map(r => r.price)))` |
| 7 | `DEALER_COMPARISON` | `/which dealers?.*(most|highest|largest)/i`, `/compare dealers/i` | **Only valid when `OEM_SCOPED_ROLES.includes(viewingAs.role)`.** If a Dealer-scoped role triggers this pattern, do not execute — fall through to a fixed response: *"Dealer comparison is only available to OEM roles."* For OEM roles: run `inventoryAgeByDealer` (§7.6) and return top 3 by average age, formatted as text. |
| 8 (fallback) | `UNRECOGNIZED` | — (no pattern matched any of the above) | Fixed response: *"I didn't understand that. Type 'help' to see what I can answer."* |

**Cross-tenant guardrail algorithm** (highest priority, checked first on every message):

```ts
function checkCrossTenantRequest(message: string, viewingAs: ViewingAs, allDealers: Dealer[]): boolean {
  if (!DEALER_SCOPED_ROLES.includes(viewingAs.role)) return false; // OEM roles have no "other dealer" concept to guard against
  const mentioned = allDealers.find(d =>
    d.dealerId !== viewingAs.dealerId &&
    message.toLowerCase().includes(d.name.toLowerCase())
  );
  return !!mentioned;
}
```
- If `true`: respond with fixed text *"I can only answer questions about your own dealership's data."*, `console.warn('[CHATBOT-GUARDRAIL] blocked cross-tenant reference:', {viewingAs, message})`, and **do not** proceed to any other intent match for that message. This mirrors the PRD's "zero cross-tenant leakage" requirement as a **client-side cosmetic demonstration only** — explicitly not a real security control (per TRD §2 scope resolution) — and must be labeled as such in code comments.
- This check relies on the dealer's `name` appearing in the message text; it will not catch every possible phrasing (e.g., typos, abbreviations). This is a known, documented limitation of the rule-based approach, not a bug to silently patch with fuzzy matching (out of scope for this prototype).

**Response function signature:**
```ts
// services.*
async function getChatbotResponse(
  viewingAs: ViewingAs,
  message: string,
  history: ChatMessage[]
): Promise<ServiceResult<{ replyText: string; intentMatched: Intent }>>
```
- `history` is accepted for interface completeness (matches TRD's note that chat should feel conversational) but **is not used** in intent resolution in this prototype — each message is matched independently, statelessly. Multi-turn context ("what about last month?" referring to a prior question) is explicitly **not supported** — falls through to `UNRECOGNIZED`. **[DECISION NEEDED]** if multi-turn context is a hard requirement — would require a larger intent-matching redesign, out of scope for rule-based matching as specified in TRD.

### 7.8 Chat UI State Machine

```
IDLE ──(user submits message)──> PROCESSING ──(services.getChatbotResponse resolves)──> IDLE
                                       │
                                       └──(throws / BAD_REQUEST)──> ERROR ──(auto, next tick)──> IDLE
```
- No `LOADING` spinner delay is artificially introduced — resolution is near-instant (in-memory regex matching); the `PROCESSING` state exists primarily to disable double-submission of the input field, not to model real latency.
- `ERROR` state does not persist visually beyond appending the fixed error bot message — it's a transition state only, not a rendered UI mode distinct from `IDLE`.

### 7.9 Vehicle Status Transition State Machine

Enforced in §7.5 validation for any `status` edit:

```
in-transit ──> in-stock ──> reserved ──> sold [terminal]
                  ▲             │
                  └─────────────┘  (reservation cancelled → back to in-stock)
```

| From \ To | in-transit | in-stock | reserved | sold |
|---|---|---|---|---|
| in-transit | — | ✅ | ❌ | ❌ |
| in-stock | ❌ | — | ✅ | ✅ |
| reserved | ❌ | ✅ | — | ✅ |
| sold | ❌ | ❌ | ❌ | — (terminal) |

Any transition marked ❌ attempted via grid edit → `BAD_REQUEST`, message: `"Invalid status transition from '<from>' to '<to>'."` A same-value "transition" (`from === to`) is a no-op, allowed silently (not an error, not a change — `services.updateVehicleField` returns success with `oldValue === newValue`, no `grid:rowUpdated` event emitted since nothing changed).

### 8.2 `dataStore.*` — Internal Module Contract (synchronous, not directly callable by `ui.*`)

```ts
// dataStore.js — internal state, exposed only to services.js

interface DataStoreState {
  schemaVersion: string;          // must match generation script output, e.g. "1.0.0"
  oem: OEM;
  dealers: Dealer[];
  vehicles: Vehicle[];
  loadedAt: string;                // ISO timestamp, set at successful load
  integrityErrors: IntegrityError[]; // populated during load, never cleared
  status: 'UNINITIALIZED' | 'LOADING' | 'READY' | 'FAILED';
}

interface IntegrityError {
  recordType: 'vehicle' | 'dealer';
  recordId: string;
  reason: string;         // e.g. "dealerId 'DLR-099' not found in dealers[]"
  excludedFromDataset: true;
}
```

```ts
dataStore.init(rawJson: unknown): void
```
- **Preconditions:** none (this is the entry point).
- **Behavior:**
  1. Set `status = 'LOADING'`.
  2. Validate top-level shape (`schemaVersion`, `oem`, `dealers`, `vehicles` all present and correctly typed). If missing/malformed → `status = 'FAILED'`, `console.error`, return (caller — `ui.appShell` — checks `dataStore.getStatus()` and emits `app:dataLoadFailed`).
  3. Run referential integrity pass (see §11.3). Exclude failing records, push to `integrityErrors`, `console.error` each.
  4. Compute derived field `daysInInventory` for every surviving vehicle (see §8.2.1).
  5. Freeze `oem` and `dealers` arrays (`Object.freeze` each element) — reference data is immutable after load per TRD/DB Engineer note. `vehicles` array elements are **not** frozen (grid editing mutates `status`/price fields in place — see §13.3).
  6. Set `loadedAt = new Date().toISOString()`, `status = 'READY'`.
- **Postconditions:** `dataStore.getStatus() === 'READY'` or `'FAILED'`. No other state is valid after `init()` returns.

```ts
dataStore.getStatus(): 'UNINITIALIZED' | 'LOADING' | 'READY' | 'FAILED'
dataStore.getRawCounts(): { oemCount: 1, dealerCount: number, vehicleCount: number, excludedCount: number }
```

#### 8.2.1 Derived Field Computation Rule

```ts
function computeDaysInInventory(vehicle: RawVehicle, asOfDate: Date): number | null {
  if (vehicle.status === 'sold' && vehicle.dateSold) {
    return dateDiffInDays(vehicle.dateReceived, vehicle.dateSold);
  }
  if (vehicle.status !== 'sold') {
    return dateDiffInDays(vehicle.dateReceived, asOfDate); // asOfDate = dataStore.loadedAt, fixed for the session
  }
  return null; // sold but dateSold missing — should have failed integrity check (§11.3); defensive fallback
}
```
`asOfDate` is captured **once** at load time and reused for the entire session (not recomputed live) so grid/chart/chatbot never disagree on "today" mid-session.

### 8.3 `dataStore.getScopedRecords(viewingAs)` — Single Source of Truth for Scoping

Per Full Stack Developer's mandate, this is the **only** function permitted to filter vehicles by role/dealer. No other module may implement its own filtering logic.

```ts
interface ViewingAs {
  role: 'OEM_ADMIN' | 'OEM_ANALYST' | 'DEALER_PRINCIPAL' | 'DEALER_STAFF';
  dealerId: string | null; // null REQUIRED for OEM_ADMIN/OEM_ANALYST, REQUIRED non-null for DEALER_* roles
}

dataStore.getScopedRecords(viewingAs: ViewingAs): { vehicles: Vehicle[], scopeValid: boolean }
```

**Validation rules (fail-closed, per Backend Engineer's mandate):**
1. `role` must be one of the 4 enumerated values — else `scopeValid: false`, `vehicles: []`.
2. If `role` is `OEM_ADMIN` or `OEM_ANALYST` → `dealerId` must be `null`. If non-null provided, `scopeValid: false`, `vehicles: []` (malformed combination — fail closed, do not silently ignore the bad dealerId).
3. If `role` is `DEALER_PRINCIPAL` or `DEALER_STAFF` → `dealerId` must be a non-null string that exists in `dataStore.dealers`. If missing or unknown → `scopeValid: false`, `vehicles: []`.
4. On `scopeValid: false`, caller (`services.*`) MUST log via `console.error('[SCOPE_FAIL_CLOSED]', viewingAs)` and return `FAIL_CLOSED_EMPTY` (see §9.1) — never fall back to unscoped/all-records.

**Filtering logic when valid:**
```ts
if (role === 'OEM_ADMIN' || role === 'OEM_ANALYST') {
  return { vehicles: dataStore.vehicles, scopeValid: true }; // full dataset, all dealers
}
// DEALER_PRINCIPAL / DEALER_STAFF
return {
  vehicles: dataStore.vehicles.filter(v => v.dealerId === viewingAs.dealerId),
  scopeValid: true
};
```

**Role-based field masking:** `DEALER_STAFF` receives the same row set as `DEALER_PRINCIPAL` (dealer-level isolation is the only isolation boundary in this prototype). Field-level permission differences between `DEALER_PRINCIPAL` and `DEALER_STAFF` (e.g. cost visibility) are **[DECISION NEEDED]** — PRD Section 5 defers final role/permission granularity. This prototype does **not** mask any fields by role beyond dealer-level row scoping. This is logged as a gap in §14 (Security Notes) and Section 18 of the TRD.

### 8.4 `services.*` — Public Contract Additions Not Yet Specified in Part 2

```ts
services.getVehicles(
```

## 9. Error Handling & Status Codes

### 9.1 `ServiceError` — Full Specification

```ts
class ServiceError extends Error {
  code: 'BAD_REQUEST' | 'FATAL' | 'SCOPE_VIOLATION' | 'SCOPE_WIDENING_ATTEMPT';
  details?: Record<string, any>;

  constructor(code: ServiceErrorCode, message: string, details?: Record<string, any>) {
    super(message);
    this.name = 'ServiceError';
    this.code = code;
    this.details = details;
  }
}
```

### 9.2 Complete Status/Error Catalog

| Code | Category | Thrown or Returned? | Trigger Condition | Caller Responsibility |
|---|---|---|---|---|
| `OK` | Success | Returned (not an exception) | ≥1 result | Render data |
| `OK_EMPTY` | Success | Returned | Valid query, 0 results | Render "no results" UI state — **not** an error state |
| `FAIL_CLOSED_EMPTY` | Security-adjacent (mock) | Returned | `viewingAs` failed validation in `getScopedRecords` | Render error banner via `service:error` event AND render empty grid/chart — never render stale/previous data |
| `BAD_REQUEST` | Programmer error | **Thrown** | Malformed params, unknown filter field, `pageSize` > 200, `SCOPE_WIDENING_ATTEMPT` | Caught by `ui.*` component, emits `service:error`, logs full `details` to console — this indicates a UI bug, not a user-facing condition |
| `FATAL` | System error | **Thrown** | `dataStore.getStatus() !== 'READY'` when a `services.*` call is made | `ui.appShell` shows full-app error state; no partial rendering |
| `SCOPE_VIOLATION` | Mock security boundary | **Thrown** | `updateVehicleField` targets a vehicleId outside current scope | Caught by `ui.dataGridView`, shows inline row-level error toast, does **not** mutate the grid |

### 9.3 UI-Level Error Handling Convention

Every `ui.*` component that calls `services.*` MUST wrap the call as follows (no exceptions to this pattern):

```ts
try {
  const result = await services.getVehicles(viewingAs, filters, sort, pagination);
  if (result.meta.scopeWarning) {
    // FAIL_CLOSED_EMPTY case — render empty state + banner, do not treat as fatal
    eventBus.emit('service:error', { code: 'FAIL_CLOSED_EMPTY', message: 'Invalid view scope', context: 'dataGridView.load' });
    renderEmptyGrid();
    return;
  }
  renderGrid(result.data, result.meta);
} catch (err) {
  eventBus.emit('service:error', {
    code: err.code ?? 'UNKNOWN',
    message: err.message,
    context: 'dataGridView.load'
  });
  renderGridErrorState();
}
```

### 9.4 `ui.errorBanner` Behavior Spec

- Listens to `service:error` and `app:dataLoadFailed`.
- Displays a dismissible banner at top of viewport: `[ERROR CODE] message`.
- Does **not** auto-dismiss (user must close it) — errors in a prototype should stay visible for debugging.
- Maintains a max of 5 stacked banners; 6th+ error replaces the oldest.
- Every banner render also triggers `console.error('[ui.errorBanner]', code, message, context)` — the banner is a visual mirror of the console log, never the only record of the error.

### 9.5 Observability / Logging Conventions (console only, per guardrails)

| Log Level | Used For | Format |
|---|---|---|
| `console.log` | Lifecycle milestones: app boot, data load success, viewingAs change | `[LIFECYCLE] <event> <details>` |
| `console.warn` | Non-fatal anomalies: empty result treated as valid, chatbot `UNRECOGNIZED` intent | `[WARN] <context> <details>` |

No log is persisted, transmitted, or exported — this is explicitly a prototype-only, session-local diagnostic aid, not an audit trail (see §10.3).

## 11. Validation Rules

### 11.1 `viewingAs` Validation (restated as canonical rule set — enforced only in `dataStore.getScopedRecords`, §8.3)

```ts
function isValidViewingAs(v: ViewingAs, knownDealerIds: Set<string>): boolean {
  const validRoles = ['OEM_ADMIN', 'OEM_ANALYST', 'DEALER_PRINCIPAL', 'DEALER_STAFF'];
  if (!validRoles.includes(v.role)) return false;
  if ((v.role === 'OEM_ADMIN' || v.role === 'OEM_ANALYST') && v.dealerId !== null) return false;
  if ((v.role === 'DEALER_PRINCIPAL' || v.role === 'DEALER_STAFF')) {
    if (typeof v.dealerId !== 'string' || !knownDealerIds.has(v.dealerId)) return false;
  }
  return true;
}
```

### 11.2 Field-Level Validation — `updateVehicleField`

| Field | Rule | Failure Behavior |
|---|---|---|
| `status` | Must be one of `'in-stock' \| 'sold' \| 'in-transit' \| 'reserved'` | `BAD_REQUEST` |
| `status` → `'sold'` | Requires `dateSold` to be set in the same logical update or already present; if neither, reject | `BAD_REQUEST` (`code: 'MISSING_DATE_SOLD'` in `details`) |
| `price` | Must be a positive number, ≤ 10,000,000 (sanity bound) | `BAD_REQUEST` |
| `dateSold` | Must be a valid ISO date, and must be **on or after** `dateReceived` for that vehicle | `BAD_REQUEST` |
| `vehicleId` (target) | Must exist in full dataset AND within current `viewingAs` scope | `SCOPE_VIOLATION` if exists-but-out-of-scope; `BAD_REQUEST` if doesn't exist at all |

### 11.3 Referential Integrity Validation (load-time, per Database Engineer input)

```ts
function validateIntegrity(rawData: RawDataset): { validVehicles: Vehicle[], errors: IntegrityError[] } {
  const dealerIds = new Set(rawData.dealers.map(d => d.dealerId));
  const errors: IntegrityError[] = [];
  const validVehicles: Vehicle[] = [];

  for (const v of rawData.vehicles) {
    if (!dealerIds.has(v.dealerId)) {
      errors.push({ recordType: 'vehicle', recordId: v.vehicleId, reason: `dealerId '${v.dealerId}' not found in dealers[]`, excludedFromDataset: true });
      continue;
    }
    if (!v.vin || !v.vehicleId) {
      errors.push({ recordType: 'vehicle', recordId: v.vehicleId ?? '(missing id)', reason: 'missing required key field', excludedFromDataset: true });
      continue;
    }
    validVehicles.push(v);
  }

  for (const d of rawData.dealers) {
    if (d.oemId !== rawData.oem.oemId) {
      errors.push({ recordType: 'dealer', recordId: d.dealerId, reason: `oemId '${d.oemId}' does not match single OEM '${rawData.oem.oemId}'`, excludedFromDataset: true });
      // dealer itself is NOT excluded from dealers[] in this prototype (single-OEM assumption makes this edge case unlikely) — but the mismatch is logged for visibility
    }
  }

  return { validVehicles, errors };
}
```
Every entry in `errors` is `console.error`'d individually at load time (§9.5) in addition to being retained in `dataStore.integrityErrors` for potential display in a debug panel (not required, optional future enhancement — not built in this prototype).

### 11.4 Chat Input Validation

- `rawText` max length: 500 characters. Longer input is truncated with a `console.warn` and processed as truncated text (not rejected — chat should never hard-fail on user typing).
- Empty/whitespace-only input: rejected client-side in `ui.chatView` before calling `services.queryChat` at all (no service call made) — not a `services.*` concern.

### 13.2 Chatbot Conversation State Machine (`ui.chatView` + `services.queryChat`)

```
[IDLE] ──user submits text──► [VALIDATING_INPUT]
   │                                │
   │                    empty/too-long (truncate) 
   │                                ▼
   │                        [MATCHING_INTENT] ── keyword match against Intent Catalog (§8.5), first match wins
   │                                │
   │                    ┌───────────┴────────────┐
   │              match found                no match found
   │                    ▼                        ▼
   │        [RESOLVING_SCOPE] (calls        [intent = UNRECOGNIZED]
   │         dataStore.getScopedRecords)          │
   │                    │                         │
   │        scopeValid=false   scopeValid=true    │
   │              ▼                  ▼            │
   │     [answer = FAIL_CLOSED   [COMPUTING_ANSWER]│
   │      generic message]        against scoped   │
   │              │              records only      │
   │              └────────┬─────────┘─────────────┘
   │                       ▼
   │              [RENDERING_RESPONSE] ── append ChatResponse to conversation log
   │                       │
   └───────────────────────┴──► back to [IDLE]
```
- Conversation history is **session-memory only**, stored as an array in `ui.chatView` closure state — lost on refresh, per TRD persistence decision.
- No multi-turn context/memory: every message is resolved independently against the Intent Catalog. Follow-up questions like "what about last week?" are **not supported** — this is a known limitation of the rule-based approach and must be stated in the chat's `HELP` response.

### 13.3 Grid Inline-Edit Workflow (`ui.dataGridView`)

```
[VIEWING] ──user clicks editable cell (status/price only, per PRD Sam Ortiz persona "edits only fields he's permitted to")──► [EDITING]
   │                                                                                                              │
   │                                                                                          user confirms (Enter/blur)
   │                                                                                                              ▼
   │                                                                                              [VALIDATING] (§11.2 rules, client-side)
   │                                                                                                              │
   │                                                                                        invalid        valid
   │                                                                                          ▼               ▼
   │                                                                              [show inline error,   services.updateVehicleField()
   │                                                                               revert cell to prior         │
   │                                                                               value] ──► [VIEWING]     success   SCOPE_VIOLATION/BAD_REQUEST
   │                                                                                                          ▼               ▼
   │                                                                                          emit grid:rowUpdated   [show inline error,
   │                                                                                          ──► [VIEWING]           revert cell] ──► [VIEWING]
```
- **Session-start snapshot for `CHANGED_THIS_WEEK` intent:** `dataStore` retains a shallow copy of each vehicle's mutable fields (`status`, `price`, `dateSold`) at `loadedAt` time, held in `dataStore._sessionStartSnapshot` (internal, not part of public contract). `grid:rowUpdated` does not mutate the snapshot — it exists only to answer "what changed" for the remainder of the session.

### 13.4 Viewing-As Switch Workflow (`ui.viewingAsSelector`)

```
[user selects new role/dealer combo]
        │
        ▼
[VALIDATE locally against known role/dealer enum] ── invalid combo (e.g. DEALER_STAFF with no dealer chosen) → disable "Apply" control, no event emitted
        │ valid
        ▼
emit 'viewingAs:changed' { role, dealerId }
        │
        ▼
Grid, Analytics, Chat each independently re-invoke their respective services.* calls with new viewingAs — no shared cache is reused across a scope change (prevents stale cross-scope data bleed-through, the closest thing to a "cache invalidation on tenant switch" rule in this mock system)
```

## 15. Deployment & Runtime Configuration

### 15.1 Runtime Configuration

There is no environment-variable-driven configuration — this is a fully static artifact. The only "configuration" is the bundled dataset file path, hardcoded:

```js
// config.js (single small module, no env vars, no build-time substitution)
const CONFIG = Object.freeze({
  DATA_FILE_PATH: './data/vehicles.json',
  DEFAULT_PAGE_SIZE: 50,
  MAX_PAGE_SIZE: 200,
  CHAT_MAX_INPUT_LENGTH: 500
});
```

### 15.2 Deployment Steps

```
1. No build step required to run.
2. Serve the project root as static files:
     Option A (simplest): open index.html directly in a browser (file:// works since fetch() targets a relative bundled JSON file served alongside it — verify no CORS restriction on the target browser for local file:// fetch; if restricted, use Option B)
     Option B (recommended): run any static file server from project root, e.g.:
         npx serve .
         (or) python3 -m http.server 8080
3. Navigate to the served root (e.g. http://localhost:8080/index.html).
```
No cloud hosting, container, or orchestration step exists per guardrails — deployment is "copy files to any static host or open locally."
