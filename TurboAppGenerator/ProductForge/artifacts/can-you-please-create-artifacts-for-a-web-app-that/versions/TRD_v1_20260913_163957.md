## 1. Document Purpose & Scope

This TRD translates PRD.md into concrete technical decisions for a **working prototype**. It defines *what* technology is used, *why*, how components interact, what business rules must be enforced, and what quality bar (performance, reliability, security posture) the build must meet.

This document does **not** contain schemas, API payload contracts, or code — those belong in SPECS.md. Where a decision requires eventual implementation detail, this document states the *requirement and rationale*; SPECS.md states the *exact shape*.

**Audience:** Frontend developer(s) implementing the prototype, and any future engineer picking this up for a production rebuild.

---

## 2. Scope Resolution: PRD Ambition vs. Prototype Reality

PRD.md describes a production-grade, multi-tenant, security-critical system: server-enforced authentication, tenant isolation, RBAC, audit logging, and a chatbot with a **zero-tolerance cross-tenant leakage** requirement. The active build profile for this exercise is **Prototype/Lightweight**, which explicitly disallows authentication, backend persistence beyond a browser-local store, and cloud infrastructure unless the *product idea itself* explicitly demands it.

**Resolution (ratified across all Round 1–3 discussion):**

- The **product idea** ("web app for OEMs and dealers with data grids, visualization, and a chatbot") governs scope — not the PRD's aspirational production posture. The product idea does not state "users must log in" or "requires an account."
- Therefore this prototype has **no authentication, no server-enforced authorization, no persistent backend, no audit trail, and no guaranteed data isolation.**
- Every PRD requirement that depends on server-side enforcement (auth, tenant isolation, audit logging, 100% chatbot leakage guarantee) is **reframed, not silently dropped**: it is implemented as a **client-side, cosmetic mock** and explicitly labeled as such in-app and in this document, so no one downstream mistakes a UI convenience for a security boundary.
- All such reframed items are logged in Section 18 (Out of Scope) as **launch-blocking gaps for any future production build.**

This is a deliberate, documented trade-off — not an oversight.

## 3. Technology Stack & Rationale

| Layer | Choice | Rationale |
|---|---|---|
| **Structure/Styling** | HTML5 + CSS3 + Tailwind CSS (via CDN) | Matches prototype default. No build step required. Tailwind gives consistent, fast styling for grids/dashboards/chat panels without a component framework. |
| **Application Logic** | Vanilla JavaScript (ES2020+), organized into `dataStore.*`, `services.*`, `ui.*` namespaces/modules | No multi-page routing and no need for a component library's state-management overhead — a single-page app with tabbed views (Grid / Analytics / Chat) satisfies all requirements. React + Vite is an *allowed alternative* but is **not chosen**: it would add a build step and dependency surface with no functional benefit at this scale. |
| **Data Visualization** | Chart.js (via CDN, no build step) | Lightweight, no-license charting library sufficient for the analytical views described in PRD §1 (bar/line/comparison charts for inventory trends, dealer comparisons). Chosen over heavier charting suites to keep the app a single self-contained file. |
| **Data Grid Rendering** | Hand-rolled HTML table + vanilla JS (sort/filter/pagination logic in `services.*`) | A full third-party grid library (e.g., AG Grid) was considered and rejected for this prototype — see "Why not X?" below. |
| **Persistence** | **None (browser session memory only).** The mock dataset is loaded once at app start from a bundled static JSON/CSV file into an in-memory JS structure (`dataStore`). No SQLite, no server DB. | The product idea does not explicitly require data to survive beyond a browser session. Per guardrails, no backend/database is assumed unless explicitly needed. If persistence across sessions becomes a real requirement, SQLite is the pre-approved next step (see Section 18). |
| **Backend/API** | **None.** All "service calls" are synchronous/async in-browser JavaScript function calls, not HTTP calls. | No server-side logic is required for filtering, aggregating, or answering pattern-matched chat queries against an in-memory dataset. |
| **Chatbot NLU** | Client-side, rule-based intent matching (keyword/pattern matching mapped to a fixed set of supported query intents) — **[ASSUMPTION]** | The product idea says "chat bot that users can talk to" but specifies no NLP technology, and guardrails forbid introducing external integrations (e.g., a hosted LLM API) unless explicitly requested. This is flagged as an assumption because a real conversational chatbot would typically call an LLM API; that is explicitly **out of scope** for this prototype (see Section 10 and Section 18). |
| **Authentication** | **None.** | Per guardrails and Section 2 scope resolution. |
| **Hosting** | Static file hosting / local dev server (open `index.html` directly, or serve via any static file server) | No cloud infrastructure needed for a client-only single-file app. |
| **Observability** | Browser console logging only | Per guardrails; no monitoring service introduced. |
| **Testing** | Manual smoke-test checklist (Section 17) | Per guardrails; no automated test framework mandated for this scope, though Vitest is an allowed future addition if the team requests automated coverage. |

### Why not X?

- **Why not a real backend (Node/Express, FastAPI, Spring)?** The product idea does not require data to persist beyond the browser, does not require multi-user concurrent write access, and does not require server-enforced security. Introducing a backend would add deployment/operational burden (a process to run, a port to manage, a database file to maintain) with no functional payoff at this scope. If real persistence or real access control becomes a stated requirement, a minimal FastAPI or Express service backed by SQLite is the pre-approved next step — not a larger framework.
- **Why not React + Vite?** React earns its cost when a project needs componentized reuse across multiple routed pages, complex shared state, or a component ecosystem (form libraries, routers). This app is a single page with three tabbed views sharing one in-memory dataset — plain JS modules with clear boundaries (`dataStore` / `services` / `ui`) achieve the same separation of concerns without a build pipeline.
- **Why not a full-featured data grid library (AG Grid, Handsontable)?** Those libraries are justified when requirements include things like drag-and-drop column reordering, virtualized rendering of 100k+ rows, or complex cell editors. PRD's data volumes (dealer inventory records) are prototype-scale; sort/filter/paginate on an in-memory array is sufficient and keeps the artifact dependency-light.
- **Why not a real LLM-backed chatbot?** This would require an external API integration (e.g., a hosted LLM provider), which the guardrails disallow by default and the product idea does not explicitly request. A rule-based intent matcher against the known data domain (vehicle inventory) can still deliver the core UX described in the PRD personas ("ask a plain-language question, get an answer") for a fixed, documented set of supported query patterns. This is the single largest capability gap versus the PRD's ambition and is called out explicitly in Section 18.
- **Why not SQLite now?** SQLite is the pre-approved database for this profile *if* server-side persistence is explicitly needed. Nothing in the product idea requires data to survive a page refresh or be shared across users/sessions, so introducing a database (and by extension a backend to talk to it) would be scope creep relative to the stated requirement.

## 4. High-Level Architecture

The prototype is a **single-page, client-only application** with three tabbed surfaces (Grid, Analytics, Chat) sharing one in-memory data source.

```
┌─────────────────────────────────────────────────────────────┐
│                     Browser (single HTML file)              │
│                                                               │
│  ┌───────────────┐   ┌───────────────┐   ┌────────────────┐ │
│  │   ui.grid     │   │  ui.analytics │   │   ui.chat      │ │
│  │ (table render,│   │ (chart render │   │ (message list, │ │
│  │  sort/filter  │   │  via Chart.js)│   │  input box)    │ │
│  │  controls)    │   │               │   │                │ │
│  └──────┬────────┘   └──────┬────────┘   └───────┬────────┘ │
│         │                   │                     │          │
│         ▼                   ▼                     ▼          │
│  ┌─────────────────────────────────────────────────────────┐│
│  │                    services.*  (business logic)          ││
│  │  getVehicles / getAnalyticsSummary / resolveChatQuery /  ││
│  │  updateVehicle / getRejectedRows / loadDataset            ││
│  │  — every function scope-filters via viewerContext first  ││
│  └───────────────────────────┬────────────────────────────┘│
│                              ▼                               │
│  ┌─────────────────────────────────────────────────────────┐│
│  │              dataStore  (in-memory dataset)               ││
│  │   Vehicles[], Dealers[], RejectedRows[]                   ││
│  │   Loaded once at startup from bundled static JSON/CSV      ││
│  └─────────────────────────────────────────────────────────┘│
│                                                               │
│  ┌─────────────────────────────────────────────────────────┐│
│  │   "Viewing As" selector (global UI control, top of page)  ││
│  │   Sets viewerContext { role, dealerId } used by ALL calls ││
│  └─────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

**Key architectural principle:** every surface (grid, chart, chatbot) reads through the **same `services.*` layer**, which reads from the **same `dataStore`**, and every service function applies the **same scoping function** (`services._applyScope`) based on the currently selected `viewerContext`. This guarantees grid, chart, and chatbot are *behaviorally* consistent with each other even though there is no real security boundary — a direct response to the BA's cross-surface consistency concern.

There are **no external dependencies at runtime** beyond two CDN-hosted static libraries (Tailwind CSS, Chart.js). Both are failure points and are addressed in Section 12 (Failure Modes).

## 5. Service Boundaries & Component Responsibilities

| Component | Responsibility | Must NOT Do |
|---|---|---|
| **`dataStore`** | Owns the raw in-memory dataset (Vehicles, Dealers, RejectedRows). Provides raw read/write primitives only. | Must not contain business logic, filtering, or scoping rules. Must not touch the DOM. |
| **`services`** | Owns all business logic: filtering, pagination, aggregation, validation, scoping enforcement, and chat-intent resolution. Every function signature takes `viewerContext` as a mandatory parameter. | Must not touch the DOM. Must not assume a caller has already applied scoping — scoping is enforced *inside* every service function, not left to the caller. |
| **`ui`** | Owns DOM rendering and event handling (grid table rendering, chart rendering via Chart.js, chat message rendering, "Viewing As" selector). Calls `services.*` and renders the returned envelope. | Must not contain business logic (no filtering/aggregation logic living in a click handler). Must not read `dataStore` directly — always go through `services`. |

This three-layer separation is a direct architectural decision from the Backend Engineer's Round 1 input, applied even though there is no network boundary — it is what makes the "Viewing As" mock scoping *safe to reason about* and what makes a future migration to a real backend a **rename/relocation of `services.*`, not a rewrite.**

## 6. Data Model & Entity Relationships

**Domain Decision (ratified per BA Final Round Input):** the prototype uses **Vehicle Inventory** as the concrete business domain, resolving PRD.md's open "[DECISION NEEDED]" item at prototype scope.

### 6.1 Entities

| Entity | Description | Relationship |
|---|---|---|
| **OEM** | The single manufacturer organization in this prototype (implicit root; not separately modeled as a UI concept since there is only one OEM in scope). | Owns many Dealers. |
| **Dealer** | A dealership. Primary grouping boundary for "Viewing As" scoping. | Belongs to the OEM; owns many Vehicles. |
| **Vehicle** | The core Record entity shown in grid/charts/chat. | Belongs to exactly one Dealer (via Dealer ID). |
| **RejectedRow** | A row from the source dataset that failed validation on load (see Section 7). Retained for visibility, excluded from the working dataset. | References the raw row data and a reason code; not linked to a Vehicle (since it never became one). |
| **viewerContext** | Not a persisted entity — a transient, in-memory object representing the currently selected "Viewing As" role and dealer scope. | Used by every `services.*` call; not stored in `dataStore`. |

### 6.2 Entity Relationship Summary (text diagram)

```
OEM (1) ──owns──> Dealer (many)
Dealer (1) ──has──> Vehicle (many)
Vehicle: belongs to exactly one Dealer (Dealer ID is a required, immutable foreign reference)
RejectedRow: independent list, not linked to Vehicle (failed rows never enter the Vehicle set)
```

### 6.3 Vehicle Attributes (business-level, not schema)

| Field | Business Meaning | Editable? |
|---|---|---|
| VIN | Unique vehicle identifier (17-character) | No — immutable once loaded |
| Dealer ID | Owning dealer; the scoping boundary | No — immutable once loaded |
| Model | Vehicle model name | Yes (per role rules, Section 8) |
| Status | One of: In Stock, In Transit, Sold, Reserved | Yes |
| Price | Sale price | Yes |
| Days In Inventory | Derived — number of days since Last Updated; recomputed, never trusted from source input | No — system-derived |
| Last Updated | Last modification date | System-managed on edit |

Full field-level type/constraint definitions belong in SPECS.md; this table establishes the business meaning and edit permissions that SPECS.md must implement exactly.

## 7. Business Rules & Data Validation

Per BA's Final Round decision, dataset loading (`services.loadDataset`) must apply the following validation rules to every incoming row before it is admitted into the working `dataStore.Vehicles` collection. This satisfies PRD P0-5's *intent* (traceable, validated data entry) at prototype scale, without a real ingestion pipeline.

| Rule | Field | Condition | Violation Behavior |
|---|---|---|---|
| VIN required & well-formed | VIN | Exactly 17 alphanumeric characters, non-empty | Reject row; reason code `INVALID_VIN` |
| VIN uniqueness | VIN | Must not duplicate an already-accepted VIN in this load | Reject row; reason code `INVALID_VIN` (duplicate) |
| Dealer must exist | Dealer ID | Must match a known Dealer in the mock Dealer list | Reject row; reason code `UNKNOWN_DEALER` |
| Model required | Model | Non-empty string | Reject row; reason code `MISSING_MODEL` |
| Status must be valid enum | Status | One of: In Stock, In Transit, Sold, Reserved | Reject row; reason code `INVALID_STATUS` |
| Price sanity range | Price | Numeric, ≥ 0, ≤ 500,000 | Reject row; reason code `PRICE_OUT_OF_RANGE` |
| Days In Inventory never trusted | Days In Inventory | Always recomputed server-side (in this case, client-side in `services`) from Last Updated; incoming value ignored | N/A — recompute, do not reject |
| Last Updated must be valid | Last Updated | Must parse as a valid ISO date; must not be in the future | Reject row; reason code `INVALID_DATE` |

**Rejected Rows Rule:** Rows failing any validation rule above are **excluded from the working dataset** but retained, in full, in a visible **"Rejected Rows" panel** (backed by `services.getRejectedRows`) showing the original row data and its reason code(s). Silent drops are explicitly disallowed — users must be able to see what failed to load and why.

**Acceptance Criteria for this section:**
- Loading a dataset containing a mix of valid and invalid rows results in: (a) all valid rows appearing in the grid, (b) all invalid rows appearing in the Rejected Rows panel with correct reason codes, (c) zero silent data loss (every input row is accounted for in either the accepted or rejected set).
- Editing a Vehicle's Status, Model, or Price through the grid re-validates against the same rules above before the in-memory record is updated; a failed edit shows an inline error and does not mutate `dataStore`.

## 8. "Viewing As" Scoping Model (Mock Role-Based Access)

This is the **cosmetic, non-enforced** replacement for PRD.md's server-side RBAC/tenant isolation requirement. It must be visibly labeled in the UI as a prototype convenience, not a security control (per BA's explicit requirement).

| Viewing As | Sees Vehicles Where | Grid Edit Rights | Chatbot Query Scope |
|---|---|---|---|
| **OEM Admin/Analyst** | All dealers (no restriction) | Read-only — no edit capability in this prototype | Can query across all dealers |
| **Dealer Principal** | Dealer ID = the selected dealer only | Can edit all fields except VIN and Dealer ID | Scoped to the selected dealer only |
| **Dealer Staff** | Dealer ID = the selected dealer only | Can edit Status and Price only (not Model) — **[ASSUMPTION: exact field-level restriction for Dealer Staff was not fully specified in prior discussion; this narrows Dealer Principal's rights per the PRD persona description of Staff as "front-line, limited access." To be validated with product owner.]** | Scoped to the selected dealer only |

**Enforcement mechanism:** The "Viewing As" control is a single global dropdown at the top of the application. Changing it updates the in-memory `viewerContext` object, which every `services.*` function reads and applies via a single shared function (`services._applyScope`). This guarantees the grid, the analytics charts, and the chatbot are all consistently scoped to the same `viewerContext` at any given moment — but it is **trivially bypassable** by any user (e.g., via browser dev tools), since there is no server to enforce it. This limitation must be displayed in-app (e.g., a persistent banner: "Prototype mode — role scoping is illustrative only, not a security boundary") and is logged as a launch-blocking gap in Section 18.

**Acceptance Criteria:**
- Switching "Viewing As" from OEM Admin to a specific Dealer immediately and consistently changes the visible rows in the grid, the data underlying the charts, and the data the chatbot will answer from — all three surfaces must update together with no stale state.
- No combination of grid filters, chart drill-downs, or chatbot phrasing can surface a Vehicle belonging to a Dealer outside the current `viewerContext` scope, *within the mocked scoping logic* (this is a functional/UX guarantee, not a security guarantee).

## 9. Service Contract Design (Function-Level API Surface)

Per the Backend Engineer's Round 3 input, the application is designed with an **API-shaped internal contract** even though there is no HTTP transport. This keeps the design consistent and makes a future real-backend migration a relocation of logic rather than a redesign.

### 9.1 Design Principles

- Every `services.*` function is a pure function of `(input, viewerContext) → result envelope`. No function touches the DOM; no function is called from inside a render loop for logging purposes.
- Every function's **first business-logic step is scope-filtering** via the shared `services._applyScope(records, viewerContext)` helper — this is centralized, not duplicated per function, so grid/chart/chatbot cannot drift out of sync.
- All functions return a consistent **result envelope** shape: a success indicator, the data payload (or error detail), and metadata (including pagination info where relevant and a request identifier for traceability in console logs). The exact envelope shape is defined in SPECS.md.
- Pagination is **mandatory and non-negotiable** on any function returning a list: default page size 25, maximum page size 100. Requests for an invalid page size are rejected with a clear error, not silently clamped — this prevents accidentally rendering an unbounded dataset into the DOM.

### 9.2 Function Surface (purpose-level, no payload contracts — see SPECS.md for exact shapes)

| Function | Purpose | Notes |
|---|---|---|
| `services.loadDataset` | Validates and loads the bundled static dataset into `dataStore` at app startup; produces a load report (accepted count, rejected rows with reason codes) | Runs once per session, on app load |
| `services.getVehicles` | Returns a scoped, filtered, paginated list of vehicles for grid rendering | Filters: Dealer, Status, Model, Price range, text search |
| `services.getVehicleById` | Returns a single scoped vehicle by ID/VIN | Used for detail/edit views |
| `services.updateVehicle` | Applies a validated, role-permitted edit to a vehicle in-memory | Re-runs Section 7 validation rules before committing; enforces Section 8 field-level edit rights |
| `services.getAnalyticsSummary` | Returns aggregated analytical data (e.g., inventory counts by status, average days-in-inventory by dealer, price distribution) scoped to `viewerContext`, for chart rendering | Feeds Chart.js visualizations directly |
| `services.getRejectedRows` | Returns the list of rows rejected during load, with reason codes | Not scoped by dealer — visible to whoever can see the load report (prototype simplification) |
| `services.resolveChatQuery` | Resolves a natural-language-style question into a supported intent, executes the matching read against scoped data, and returns a conversational-style answer | See Section 10 for detail |

### 9.3 Endpoint-Equivalent Naming (for future backend migration clarity)

If this prototype is later promoted to a real backend, the intended REST-equivalent surface is:

| Prototype Function | Future REST Equivalent | Purpose Target Latency |
|---|---|---|
| `getVehicles` | `GET /api/vehicles` | p95 < 200ms for a paginated (≤100 rows) response |
| `getVehicleById` | `GET /api/vehicles/{id}` | p95 < 100ms |
| `updateVehicle` | `PATCH /api/vehicles/{id}` | p95 < 200ms |
| `getAnalyticsSummary` | `GET /api/analytics/summary` | p95 < 500ms (aggregation cost) |
| `getRejectedRows` | `GET /api/ingestion/rejected-rows` | p95 < 200ms |
| `resolveChatQuery` | `POST /api/chat/query` | p95 < 1s (includes intent resolution) |

These targets are documented now as the **design intent** for the client-side prototype's perceived responsiveness (Section 11 restates them as NFRs), even though there is no network round-trip today.

## 10. Chatbot Design & Query Resolution Strategy

**[ASSUMPTION]** The product idea specifies only that users must be able to "talk to" a chatbot; it does not specify the underlying NLP technology. Given the guardrails prohibit introducing an external LLM/API integration by default, this prototype implements the chatbot as a **rule-based, pattern-matched intent resolver** against a fixed, documented set of supported query types. This is a significant, deliberate capability gap versus the PRD's "ask anything" framing, and it is logged as a production roadmap item in Section 18.

### 10.1 Supported Intent Categories (illustrative, to be finalized in SPECS.md)

| Intent Category | Example Phrasing | Resolves To |
|---|---|---|
| Inventory count by status | "How many vehicles are in stock?" | `getAnalyticsSummary` filtered by Status |
| Dealer comparison (OEM view only) | "Which dealer has the most vehicles in transit?" | `getAnalyticsSummary` grouped by Dealer |
| Aging inventory lookup | "What vehicles have been in inventory longest?" | `getVehicles` sorted by Days In Inventory desc |
| Price lookup | "What's the average price of vehicles in stock?" | `getAnalyticsSummary` aggregation |
| Record lookup by VIN | "Show me VIN 1FA..." | `getVehicleById` |
| Unrecognized query | Anything not matching a known pattern | Explicit "I don't understand that yet" fallback response — never a silent failure or a fabricated answer |

### 10.2 Behavioral Requirements

- The chatbot **must** apply the same `viewerContext` scoping as the grid and charts — it answers only from data the current "Viewing As" selection is scoped to. This is enforced by routing every chatbot answer through the same `services.*` functions used by the grid/chart surfaces (Section 9), never through a separate/duplicated data path.
- The chatbot must **never fabricate an answer** for an unrecognized query — it must return an explicit fallback message rather than guessing.
- Every chatbot exchange (question text, matched intent, resolved answer, active `viewerContext`) is logged to the browser console per Section 13, for demo/debug traceability.

### 10.3 Acceptance Criteria

- For each documented intent category, a representative phrasing produces a correct, scope-respecting answer against the loaded mock dataset.
- A query attempting to ask about a dealer outside the current `viewerContext` scope (e.g., a Dealer Principal asking about a different dealer's inventory) returns a scope-respecting answer (i.e., it answers only for the dealer in scope, or explicitly states the question is out of scope for the current view) — never leaks data from another dealer.
- An unrecognized/out-of-domain query (e.g., "what's the weather") returns the explicit fallback message, not an error, crash, or fabricated answer.

## 11. Non-Functional Requirements

| Category | Requirement | Target / Threshold |
|---|---|---|
| **Grid load latency** | Time from "Viewing As" or filter change to grid re-render | < 300ms for a dataset of up to ~2,000 mock vehicle records (in-memory filter/sort, no network) |
| **Chart render latency** | Time from filter change to chart re-render | < 500ms |
| **Chatbot response latency** | Time from submitted question to displayed answer | < 1s for any supported intent |
| **Pagination** | Grid must never render the full unbounded dataset at once | Default page size 25 rows; max 100 rows per page |
| **Data load integrity** | Every row in the source dataset must end up in exactly one of: accepted Vehicles set, or Rejected Rows set | 100% accounted for; zero silent drops |
| **Cross-surface consistency** | Grid, chart, and chatbot must reflect the same `viewerContext` scope at all times | 100% consistency within the mocked scoping logic (functional guarantee, not a security guarantee — see Section 12) |
| **Availability** | Single-page client-only app; no server dependency for core function | App must remain fully functional (grid/chart/chat against already-loaded data) if CDN-hosted libraries (Tailwind, Chart.js) fail to load *after* initial successful load; a failed *initial* load of these libraries degrades gracefully (see Section 12 failure modes) |
| **Browser support** | Target modern evergreen browsers (Chrome, Edge, Firefox, Safari, latest 2 major versions) | No legacy browser support required — not stated in product idea |
| **Data volume** | Prototype dataset size | Designed and tested for up to ~2,000 mock Vehicle rows across a small set of mock Dealers; no requirement to scale beyond prototype demo volumes |

## 12. Security & Data Protection Posture

This section states the security posture **honestly**, per guardrails ("never skip security design... document trade-offs explicitly").

### 12.1 What this prototype provides

- Client-side scoping logic (`viewerContext` + `services._applyScope`) that produces **consistent, role-appropriate UX** across grid/chart/chatbot for demo purposes.
- Input validation on data load (Section 7), preventing malformed records from corrupting the in-memory dataset or downstream chart/chatbot calculations.
- No transmission of data to any external server (since there is no backend and no third-party API call), so there is no network-based data exfiltration surface beyond the two CDN library loads (Tailwind CSS, Chart.js — neither receives application data).

### 12.2 What this prototype explicitly does NOT provide

- **No authentication.** Anyone with the URL/file can open the app and select any "Viewing As" role, including OEM Admin, with full visibility into all mock dealers' data.
- **No server-enforced authorization.** The scoping in Section 8 is a UI convenience, trivially bypassed via browser developer tools (e.g., directly inspecting `dataStore` in the JS console).
- **No audit trail.** There is no persistent record of who viewed/edited what — only ephemeral browser console logs for the current session (Section 13).
- **No guarantee against cross-tenant data leakage** in the sense the PRD requires (100% zero-tolerance, QA-verified). The chatbot and grid *behaviorally* respect the current `viewerContext`, but this is not a security boundary and must never be represented as one in a demo or pilot.

### 12.3 Failure Modes for External Dependencies

| Dependency | Failure Mode | Mitigation |
|---|---|---|
| Tailwind CSS CDN | CDN unreachable at page load | Page still functions (unstyled/minimally styled); functionality is not blocked, only visual polish. Recommended mitigation for any real deployment: vendor the CSS file locally instead of relying on CDN. |
| Chart.js CDN | CDN unreachable at page load | Analytics tab shows a clear "Charts unavailable" message rather than a blank/broken tab; grid and chatbot remain fully functional since they do not depend on Chart.js. |
| Bundled static dataset file | Malformed/missing dataset file | `services.loadDataset` reports a load failure explicitly (not a silent empty grid); app shows a clear "No data loaded" state across all three tabs. |

### 12.4 Mandatory In-App Disclosure

The application **must** display a persistent, visible notice (e.g., a banner or footer text) stating that role/dealer scoping is a prototype convenience and not a security control, and that no data leaves the browser. This is a functional requirement, not optional polish — it directly addresses the BA's explicit concern that this distinction must never be silently lost.

## 13. Observability & Logging Strategy

Per guardrails, observability is limited to **browser console logging** — no monitoring/APM service is introduced.

| Event | Logged Data | Purpose |
|---|---|---|
| Dataset load | Row counts (accepted/rejected), reason code breakdown | Debug data quality issues during demo |
| `viewerContext` change ("Viewing As" switch) | New role, new dealer ID | Trace scoping behavior during demo/QA |
| Every `services.*` call | Function name, key input parameters (filters, ids), resulting record count, a generated request identifier | Correlate grid/chart/chatbot behavior back to a single logical request for debugging |
| Chatbot exchange | Question text, matched intent (or "unrecognized"), active `viewerContext`, resolved answer summary | Debug chatbot intent-matching quality; support the PRD's underlying goal of traceable chatbot behavior, at prototype scope |
| Validation rejection | Row data, reason code | Support the Rejected Rows panel and general debugging |

Logging must occur **once per call boundary**, not inside loops (per guardrails), to avoid console flooding when operating on paginated or filtered sets.

## 14. Error Handling Strategy

- Every `services.*` function returns a consistent success/failure result envelope (exact shape defined in SPECS.md) — grid, chart, and chatbot surfaces all consume this same shape, so error rendering logic in `ui.*` is written once and reused, not duplicated per surface.
- Error messages surfaced to the user must be **human-readable and free of internal implementation detail** (e.g., no raw stack traces or internal variable names shown in the UI).
- Categories of errors the system must handle explicitly:
  - **Validation errors** (Section 7) — surfaced per-row in the Rejected Rows panel, and per-field on inline grid edits.
  - **Invalid pagination requests** — rejected with a clear message, never silently clamped (Section 9.1).
  - **Unrecognized chatbot queries** — explicit fallback message (Section 10.2), never a fabricated answer or a raw error.
  - **Missing/corrupt dataset file** — explicit "No data loaded" state across all tabs (Section 12.3).
- All errors are logged to the console with the associated request identifier (Section 13) for debugging, in addition to being rendered to the user.

## 15. Data Flows

### 15.1 Application Startup / Data Load Flow

1. App loads in browser; `dataStore` is empty.
2. `services.loadDataset` is invoked automatically, reading the bundled static dataset file.
3. Each row is validated against Section 7 rules.
4. Valid rows populate `dataStore.Vehicles`; invalid rows populate `dataStore.RejectedRows` with reason codes.
5. A load report (counts, breakdown) is logged to console and made available via `services.getRejectedRows` for the Rejected Rows panel.
6. Default `viewerContext` is set (e.g., OEM Admin, all dealers) and the Grid tab renders.

### 15.2 Grid Interaction Flow

1. User changes "Viewing As," a filter, sort order, or page.
2. `ui.grid` calls `services.getVehicles(filters, pagination, viewerContext)`.
3. `services.getVehicles` applies scoping (`_applyScope`) first, then filters/sorts/paginates, then returns the result envelope.
4. `ui.grid` renders the returned rows and pagination controls.

### 15.3 Analytics Flow

1. User switches to the Analytics tab or changes `viewerContext`/filters.
2. `ui.analytics` calls `services.getAnalyticsSummary(filters, viewerContext)`.
3. `services.getAnalyticsSummary` applies scoping, computes aggregates (counts by status, average days-in-inventory, etc.), and returns the result envelope.
4. `ui.analytics` feeds the returned aggregates into Chart.js chart instances.

### 15.4 Chatbot Flow

1. User submits a question in the Chat tab.
2. `ui.chat` calls `services.resolveChatQuery(text, viewerContext, conversationId)`.
3. `resolveChatQuery` pattern-matches the text against the supported intent list (Section 10.1); on a match, it internally calls the relevant read function (`getVehicles` / `getAnalyticsSummary` / `getVehicleById`), which itself applies scoping.
4. On no match, it returns the explicit fallback envelope.
5. `ui.chat` renders the answer (or fallback) as a chat bubble and logs the exchange (Section 13).

### 15.5 Edit Flow

1. User edits a field in the grid (where permitted by Section 8's role/field matrix).
2. `ui.grid` calls `services.updateVehicle(id, patch, viewerContext)`.
3. `updateVehicle` checks field-level edit permission for the current role, re-validates the patched value against Section 7 rules, and — if valid and permitted — updates `dataStore.Vehicles` and recomputes Days In Inventory.
4. On any failure (permission or validation), the function returns a failure envelope; `dataStore` is left unmodified.

## 16. Deployment Topology

- The application is delivered as a **static, self-contained set of files** (HTML entry point, JS modules, one bundled static dataset file), suitable for:
  - Opening directly in a browser from the local filesystem, or
  - Serving via any static file server (e.g., a simple local dev server) — no application server process required.
- No environment-specific configuration, secrets, or environment variables are required, since there is no backend and no external API integration.
- No containerization, orchestration, or cloud hosting service is introduced, per guardrails — this is intentionally the simplest deployment topology that satisfies the requirement.

## 18. Out of Scope / Deferred to Production Roadmap

The following PRD.md requirements are **explicitly acknowledged and intentionally not implemented** in this prototype. They must be carried forward as launch-blocking items for any production build, per BA's Round 1 direction — not silently dropped.

| PRD Requirement | Status Here | Required for Production |
|---|---|---|
| Server-enforced authentication (login/accounts) | Not implemented | Yes — must be added before any real user data is involved |
| Server-enforced tenant isolation / RBAC | Not implemented (client-side mock only) | Yes — a real backend + authorization layer is required |
| Zero-tolerance cross-tenant chatbot leakage (100% QA-verified) | Not achievable without server-side enforcement | Yes — requires backend-enforced data access before the chatbot queries any data store |
| Persistent audit trail of access/edits, reviewed weekly | Not implemented (console logs only, non-persistent) | Yes — requires backend + database + retention policy |
| Production data ingestion pipeline (multi-source: dealer-entered, OEM systems, spreadsheets) | Partially represented via static dataset validation rules only | Yes — real ingestion, dedupe-across-sources, and scheduling are required |
| LLM-backed natural-language chatbot (open-ended question answering) | Replaced with rule-based intent matching over a fixed, documented set of query types | Yes, if "ask anything" conversational capability is a hard product requirement — would require an approved external LLM integration and associated data-privacy review |
| Persistent, multi-session data storage (SQLite or similar) | Not implemented — dataset is in-memory only, reset on reload | Yes, if data must survive beyond a single browser session or be shared across users |
| Full audit of data access violations reviewed weekly (PRD success metric) | Not measurable without persistent audit logging | Yes |
