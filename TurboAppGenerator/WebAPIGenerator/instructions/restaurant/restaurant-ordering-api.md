# Restaurant Ordering API

## Overview

A food-ordering platform: restaurants, their menus, customers, and orders
composed of multiple line items. Different shape from the other sample
domains specifically to exercise an order-with-line-items pattern (create
the parent and every child row in one call, each line item snapshotting its
own price at order time) and revenue/rating rollups computed across that
parent-child join, not stored as a running total.

## Suggested form settings (API options)

- Language: Python (FastAPI) or Java (Spring Boot) — either works
- Auth type: Basic Auth
- Rate limit: 100 (req/min)

---

## Resources

### Restaurants
Fields: id, name, cuisine_type (italian / mexican / chinese / indian /
american), city, created_at.

### MenuItems
Fields: id, restaurant_id (FK → restaurants.id), name, category
(appetizer / main / dessert / beverage), price, is_available, created_at.

### Customers
Fields: id, name, email (unique), phone, created_at.

### Orders
One row per order — its own total is never stored as a column, always
computed from its OrderItems. Fields: id, customer_id (FK → customers.id),
restaurant_id (FK → restaurants.id), status
(placed / preparing / out_for_delivery / delivered / cancelled), order_date,
created_at.

### OrderItems
Fields: id, order_id (FK → orders.id), menu_item_id (FK → menu_items.id),
quantity, unit_price_at_time (snapshot of the menu item's price at the
moment it was ordered — never recomputed from today's price on read, even
if the restaurant later changes that item's price), created_at.

### Reviews
Fields: id, restaurant_id (FK → restaurants.id), customer_id
(FK → customers.id), order_id (FK → orders.id), rating (integer 1-5),
comment, created_at.

## Endpoints

### Catalog
- `GET /restaurants` — list all; support `cuisine_type` and `city` filters
- `GET /restaurants/{id}` — **complex join**: the restaurant plus its full
  menu (every MenuItem)
- `GET /menu-items` — list all; support `restaurant_id` and `category`
  filters
- `POST /restaurants` — create
- `POST /menu-items` — create

### Orders
- `POST /orders` — create an order AND its line items in one call (request
  body includes an `items` array of `{menu_item_id, quantity}`); reject with
  400 if any referenced menu item's `is_available` is false; capture each
  item's `unit_price_at_time` from that menu item's CURRENT price at
  creation
- `GET /orders/{id}` — **complex join**: the order plus the customer's name,
  the restaurant's name, every OrderItem with its menu item's name and a
  computed line total (`quantity * unit_price_at_time`), and a computed
  `total_amount` = sum of all line totals
- `PATCH /orders/{id}/status` — update order status only

### Customers
- `GET /customers` — list all
- `GET /customers/{id}/orders` — **complex join**: this customer's order
  history, each with the restaurant's name and that order's computed
  `total_amount`

### Reviews
- `POST /reviews` — create (reject with 400 if `rating` isn't 1-5, or if
  `order_id` doesn't belong to `customer_id`)

### Reporting (multi-table aggregates)
- `GET /restaurants/{id}/revenue-report` — **complex join**: total order
  count, total revenue (sum of every order's computed total), and a
  breakdown of revenue by menu category (joining orders → order_items →
  menu_items), for that restaurant only
- `GET /restaurants/{id}/reviews-summary` — **complex join**: review count,
  average rating, and a count breakdown by rating value (1 through 5)
- `GET /menu-items/{id}/popularity` — **complex join**: total quantity ever
  ordered across all orders, and total revenue generated by that item

## Data Rules

- `Customers.email` must be unique; reject duplicates with 400.
- An order's total is NEVER a stored column — always computed from its
  OrderItems' `quantity * unit_price_at_time`, every time it's requested.
- `OrderItems.unit_price_at_time` is captured once at creation from the
  menu item's price at that moment — it must never be recomputed from
  today's price on read, even for old orders after a price change.
- An order can't include a menu item whose `is_available` is currently
  false — reject the whole order with 400 and a clear message.
- `Reviews.rating` must be an integer 1-5 — reject otherwise with 400.
- Seed data: 4 restaurants across different cuisines, 6-8 menu items per
  restaurant (at least 3 categories represented per restaurant), 10
  customers, 15 orders spread across multiple restaurants and every status
  value, with realistic multi-item OrderItems for each (2-4 items per
  order), and 12 reviews spread across restaurants and rating values —
  enough that every complex-join endpoint above returns realistic,
  non-empty, multi-row results out of the box.
