1. What is Model Context Protocol (MCP)?

Model Context Protocol (MCP) is an open standard protocol developed by Anthropic that enables seamless integration between Large Language Models (LLMs) and external data sources, tools, and services.

Core Purpose

MCP solves a fundamental challenge in AI applications: how to provide LLMs with secure, controlled access to external context and capabilities without hardcoding integrations. Instead of building custom integrations for each tool or data source, MCP provides a standardized protocol that works across different LLMs and platforms.

Key Benefits

🔌 Standardized Integration

Single protocol for connecting any LLM to any data source or tool

🔒 Security & Control

Built-in authentication, authorization, and data governance

🚀 Extensibility

Easy to add new capabilities without modifying the core LLM

♻️ Reusability

MCP servers can be shared and reused across different applications

🎯 Context Awareness

LLMs gain access to real-time, relevant data for better responses

🛠️ Tool Augmentation

Extend LLM capabilities with custom functions and APIs

MCP Protocol Components

📦 Resources

Structured data that LLMs can read (files, database records, API responses, documentation)

🔧 Tools

Functions that LLMs can execute (API calls, database queries, file operations, calculations)

💬 Prompts

Reusable prompt templates with variables for consistent AI interactions

💡 Key Insight: MCP acts as a "universal adapter" between LLMs and external systems, similar to how USB-C standardized device connections.

Architectural Layers

Layer 1: MCP Client (LLM Application)

  • The AI assistant or application using the LLM
  • Sends requests to MCP servers to access tools/resources
  • Examples: Claude Desktop, VS Code with Copilot, custom chat applications

Layer 2: MCP Host

  • Manages connections between clients and servers
  • Handles authentication, routing, and session management
  • Can run multiple MCP servers simultaneously
  • Typically embedded in desktop applications or IDEs

Layer 3: MCP Server

  • Implements the MCP protocol specification
  • Exposes tools, resources, and prompts to clients
  • Handles requests via JSON-RPC 2.0 over STDIO or HTTP
  • Can be written in any language (Python, TypeScript, Go, etc.)

Layer 4: Backend Services

  • The actual data sources, APIs, databases, or tools
  • MCP servers act as adapters to these services
  • Can include: SQL databases, REST APIs, file systems, cloud services

Communication Protocol

Transport Mechanisms

  • STDIO Standard Input/Output for local processes
  • HTTP/SSE HTTP with Server-Sent Events for remote connections
  • WebSocket For bi-directional streaming (future)

Message Format

All MCP communication uses JSON-RPC 2.0 format:

{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "query_database",
    "arguments": {
      "query": "SELECT * FROM customers"
    }
  },
  "id": 1
}

3. LLM-Based Ecosystem with Third-Party MCPs

End-to-End Architecture Flow

Complete Layer Stack: Client to Backend

Detailed Request/Response Flow

Step-by-Step Communication

  1. 👤 User Query: User asks "Show my open GitHub pull requests" in Claude Desktop
  2. 🤖 LLM Analysis: Claude determines it needs GitHub data and identifies available MCP tools
  3. 🔍 MCP Discovery: Host provides list of registered servers (GitHub MCP is available)
  4. 🎯 Tool Selection: Claude selects github_list_prs tool with parameters
  5. 📦 Request Formatting: Host creates JSON-RPC message: 
    {
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {"name": "github_list_prs", "arguments": {"state": "open"}},
  "id": 1
}
  6. 🔌 STDIO/HTTP Transport: Host sends request to GitHub MCP Server via configured transport
  7. ⚙️ MCP Server Processing: GitHub MCP Server validates request and authenticates with GitHub API
  8. 🌐 API Call: Server makes REST call: GET https://api.github.com/repos/{owner}/{repo}/pulls?state=open
  9. 📥 Data Retrieval: GitHub API returns JSON with PR data
  10. 🔄 Response Formatting: MCP server formats data according to protocol and returns to host
  11. 📤 Context Integration: Host provides formatted data to Claude as context
  12. ✍️ Answer Generation: Claude generates natural language response: "You have 3 open PRs: ..."

Working with Third-Party MCP Servers

Discovery & Registration

MCP servers are registered in the host application's configuration file:

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "your_token_here"
      }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": {
        "POSTGRES_CONNECTION": "postgresql://localhost/mydb"
      }
    }
  }
}

Capability Advertisement

When an MCP server starts, it advertises its capabilities:

  • Tools: List of available functions with parameter schemas
  • Resources: Available data sources with URIs and types
  • Prompts: Reusable templates with variable definitions

4a. NLP to Structured/Semi-Structured Data MCP Server

📊 Purpose

Transform natural language queries into intelligent analysis of structured and semi-structured data formats (Excel, JSON, CSV, PSV) without requiring users to know query languages or data structures.

Architecture Overview

User NL Query
"Top 5 sales reps"
→
NLP MCP Server
Query Parser
→
Data Processor
Pandas/Analysis
→
Formatted Results
Tables/Charts

Key Components

1. Data Ingestion Layer

  • Multi-format Support: Excel (.xlsx, .xls), CSV, JSON, PSV (Pipe-Separated)
  • Metadata Management: Optional JSON metadata for column descriptions, data types, relationships
  • Smart Detection: Automatic delimiter detection, encoding handling, data type inference
  • Caching: Efficient data loading with in-memory caching for repeat queries

2. NLP Query Parser

  • Intent Extraction: Identifies query type (filter, aggregate, group, sort, limit)
  • Entity Recognition: Maps natural language terms to actual column names using fuzzy matching
  • Metric Detection: Identifies target metrics (sum, average, count, max, min)
  • Context Awareness: Understands date ranges, comparisons, thresholds

Example Transformations:

Natural Language Query Parsed Intent
"Show top 5 sales by region" group_by=region, metric=sales, sort=desc, limit=5
"Average revenue for each product" group_by=product, metric=revenue, aggregation=mean
"Customers with orders over $1000" filter=order_amount>1000, display=customer_records

3. Data Analysis Engine

  • Pandas Integration: Leverages Pandas for efficient data manipulation
  • Aggregation Support: Sum, mean, median, count, min, max, std deviation
  • Grouping & Pivoting: Multi-level grouping, pivot tables, cross-tabulation
  • Filtering: Complex conditions with AND/OR logic
  • Sorting & Ranking: Multiple sort keys, top-N queries, percentile ranking

4. Response Formatting

  • Structured Output: JSON, Markdown tables, CSV export
  • Visualization Support: Integration with chart generation tools
  • Statistical Summaries: Automatic descriptive statistics when appropriate
  • Human-Readable: Natural language explanations of results

MCP Tools Exposed

Tool Name Purpose Parameters
load_data Load data file with optional metadata file_path, file_type, metadata_path
intelligent_query Execute natural language query on loaded data query (NL string), output_format
get_data_summary Get statistical summary of loaded dataset include_distributions, column_list
export_results Export query results to file format (csv/json/excel), output_path

Usage Example

# User in chat interface
User: "Load the Q4 sales data and show me the top 10 customers by revenue"

# MCP Tool Calls (handled automatically)
1. load_data(file_path="Q4_Sales.xlsx", file_type="excel")
   → Returns: "Loaded 2,547 records with 12 columns"

2. intelligent_query(query="top 10 customers by revenue")
   → Parses: group_by=customer_name, metric=revenue, 
              aggregation=sum, sort=desc, limit=10
   → Returns: Formatted table with customer names and revenue totals

Benefits Over Direct SQL

  • ✅ No Schema Knowledge Required: Users don't need to know table structures or column names
  • ✅ Works with Files: No database setup needed - works directly with Excel, CSV, JSON
  • ✅ Fuzzy Matching: Tolerates typos and variations in column name references
  • ✅ Context-Aware: Understands business terms without explicit mapping
  • ✅ Flexible Formats: Handles semi-structured data that doesn't fit relational models

4b. NLP to Custom API MCP Server

🔌 Purpose

Enable natural language interaction with custom REST APIs, internal microservices, and business logic layers without requiring users to understand API endpoints, parameters, or authentication mechanisms.

Example: Complete API Request Flow

Real-World Scenario: "Show high-risk projects in Auto Insights"

Layer Action Technical Details
Client User types query "Show all high-risk projects in the Auto Insights portfolio"
MCP Host Routes to API server {"method": "tools/call", "params": {"name": "query_api", "arguments": {"query": "high-risk projects Auto Insights"}}}
Intent Mapper Parses query intent Entity: "Auto Insights" (portfolio), Filter: "high-risk" (risk_level), Action: "list projects"
API Orchestrator Plans API calls Step 1: Get portfolio ID → Step 2: Query projects with filters
API Call 1 Fetch portfolio GET /api/pmo/portfolios?name=Auto%20Insights
→ Returns: {"id": "PF-001"}
API Call 2 Fetch projects GET /api/pmo/projects?portfolio_id=PF-001&risk_level=high
→ Returns: Array of 3 projects
Response Processor Aggregates & formats Combines data from multiple calls, adds metadata, creates table
MCP Server Returns to host JSON-RPC response with formatted project list
Client LLM generates answer "Found 3 high-risk projects in Auto Insights: 1. Customer Churn Prediction (85% budget used)..."

Why This Replaces NLP-to-SQL

Modern Architecture Shift: Many organizations have moved from direct database access to API-first architectures. This MCP server allows LLMs to interact with these APIs naturally, providing:
  • ✅ Better Security: APIs enforce business rules and access controls
  • ✅ Business Logic Enforcement: APIs encapsulate calculations, validations, workflows
  • ✅ Microservices Support: Seamlessly work across distributed systems
  • ✅ Real-time Data: APIs can aggregate from multiple sources, caches, external services

Key Components

1. API Configuration Layer

  • Endpoint Registry: Catalog of available APIs with descriptions
  • Schema Definitions: OpenAPI/Swagger specs for parameter validation
  • Authentication Config: Support for OAuth, API keys, JWT, basic auth
  • Rate Limiting: Built-in throttling and retry logic

Example Configuration:

{
  "apis": {
    "project_management": {
      "base_url": "https://api.internal.com/pmo",
      "auth_type": "bearer",
      "endpoints": {
        "get_projects": {
          "path": "/projects",
          "method": "GET",
          "description": "List all projects with optional filters",
          "parameters": {
            "status": "string (active|completed|on-hold)",
            "portfolio": "string",
            "start_date": "date (YYYY-MM-DD)"
          }
        },
        "get_project_details": {
          "path": "/projects/{project_id}",
          "method": "GET",
          "description": "Get detailed info for specific project"
        }
      }
    }
  }
}

2. Intent Mapping Engine

  • Query Classification: Determines which API(s) to call based on natural language
  • Parameter Extraction: Identifies and validates API parameters from user query
  • Multi-API Orchestration: Chains multiple API calls when needed
  • Context Preservation: Maintains conversation state for follow-up queries

Example Mappings:

Natural Language API Call(s)
"What are the active projects in Finance portfolio?" GET /projects?status=active&portfolio=Finance
"Show me project P12345 budget details" GET /projects/P12345/budget
"List overdue tasks for Sarah's team" GET /teams?lead=Sarah → GET /tasks?team_id={id}&status=overdue

3. API Orchestration Layer

  • Request Builder: Constructs API requests with proper headers, auth, parameters
  • Parallel Execution: Makes concurrent API calls when possible
  • Error Handling: Graceful handling of timeouts, rate limits, errors
  • Response Caching: Optional caching for frequently-accessed data
  • Data Transformation: Normalizes responses from different APIs

4. Response Processing

  • Data Aggregation: Combines results from multiple API calls
  • Formatting: Presents data in user-friendly formats (tables, summaries, charts)
  • Enrichment: Adds context and explanations to raw API data
  • Filtering: Applies additional filters based on query intent

MCP Tools Exposed

Tool Name Purpose Parameters

list_available_apis Show all configured APIs and their capabilities category (optional filter)

               {id: "P-456", name: "Real-time Analytics", ...}
             ]

             GET /projects/P-123/budget
             GET /projects/P-456/budget
